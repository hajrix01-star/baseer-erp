# معالجة عرض العمليات المستوردة من نوركس — 2026-08-30

## النطاق

هذا التغيير **عرض فقط** للقيود المالية التاريخية المستوردة في ARZ ومشويات المعلم الشامي. لا يغيّر قيوداً مختومة أو مبالغاً أو تواريخ أو `sourceReference` المحفوظ للتدقيق.

## المشكلة والسبب الجذري

كانت طبقات العرض تتعامل مع أنواع `nurix_*` على أنها مصدر غير معروف؛ لذلك تعرض تسمية عامة مثل «حركة مالية خارجة» ومرجعاً تقنياً (`cmr...` أو `NOORIX-XLSX:...`) رغم وجود رقم تجاري في علاقة العملية أو وصف الترحيل.

## الدليل

فحص القراءة في قاعدة الاختبار أحصى **2,387** قيداً مستورداً:

| نوع البيانات | العدد |
| --- | ---: |
| فواتير مشتريات/مصروف تاريخية | 2,142 |
| سلف موظفين وتسوياتها | 175 |
| مسيرات رواتب ومدفوعاتها | 22 |
| مصروفات دورية/دليل تاريخي | 48 |
| الإجمالي | 2,387 |

المثال الذي كشف المشكلة كان قيداً بمعرف `cmr41c4…` ووصفه المحفوظ: `سلفة تاريخية نوركس: ADV-20260702-002`. الأعداد توثق العرض فقط، ولا تعد مطابقة مالية أو بديلاً عن تقارير الإغلاق.

## الحل

- أُنشئ مفسر موحد في `finance-journal-presentation.ts` لأنواع Noorix: فاتورة شراء/مصروف، مصروف دوري، سلفة/سداد سلفة، واستحقاق/سداد مسير.
- أولوية المرجع: علاقة العمل المستهدفة، ثم الرقم التجاري الموثق في الوصف، مع منع إظهار CUID/UUID/بصمة Excel للمستخدم افتراضياً.
- تستخدمه الآن واجهات السجل المالي والحسابات والخزائن والتقارير النقدية وميزان المراجعة والضريبة وملف الموظف.
- تُبقي الواجهة المرجع التقني محفوظاً في القيد للتدقيق الإداري فقط.

## التحقق والوقاية

- نجح `npm run check --workspace @baseer-erp/api`.
- نجح `npm run check --workspace @baseer-erp/web`.
- نجح build للـAPI واختبار `finance-journal-presentation.policy-verification` لكل أنواع Noorix المكتشفة.
- أُعيد تشغيل API المحلي وتحقق endpoint الجاهزية `GET /v1/health/ready` بحالة `200`.

## شرط الخروج

يجب تحديث صفحة المتصفح مرة واحدة. تظهر السلفة في المثال باسم **«سلفة موظف تاريخية»** ومرجع **`ADV-20260702-002`**، ولا يظهر `cmr...` في العرض التشغيلي.
