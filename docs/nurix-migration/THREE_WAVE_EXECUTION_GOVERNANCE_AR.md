# حوكمة تنفيذ ترحيل نوركس إلى بصير — ثلاث موجات

**الحالة:** معتمدة كخطة التنفيذ. لا تعني الاعتماد الموافقة على إدخال بيانات أعمال الآن.  
**النطاق:** الأرشيف ذو البصمة `D8836B78AB52B8C297D87115767314E0560A2C09993000C0C503E5BA27C7B9AD`، وقاعدة `baseer_migration_staging` فقط إلى أن يصدر قرار Go مستقل.

## قواعد لا تتغير

1. لا SQL مباشر إلى جداول أعمال بصير ولا تبديل للـIDs المصدرية.
2. كل قراءة من نوركس تكون من النسخة المعزولة المحددة بالبصمة، وكل قرار/خريطة/receipt يكون append-only ومقيدًا بالـtenant وRLS.
3. لا استيراد جزئي إلى بيئة تشغيل: يجوز تحليل الشركات منفردة، لكن لا يبدأ staging لأي شركة من النطاق المعتمد ما لم تجتز كل الشركات بوابة الموجة نفسها.
4. أي اختلاف في البصمة، checksum، عدد السجلات، أو توازن مالي يحول الحالة إلى **NO-GO** ولا يعالج بإعادة تشغيل صامتة.
5. المرفقات غير الموجودة في الأرشيف تظل `BLOCKED`؛ لا تنشأ ملفات بديلة ولا روابط مكسورة.

## الموجة 1 — الأساس والبيانات الرئيسية

**الهدف:** إنتاج run جديدة موثقة وجاهزة لـdry-run، من دون فواتير أو قيود أو موظفين.

**المدخلات والحواجز:**

- حسم 351 قرار هوية مورد متبقٍ؛ القرار اليدوي ينشئ alias صريحًا أو هوية تجارية مستقلة فقط.
- اعتماد company maps الثماني عبر `APPROVE_COMPANY_MAPS`؛ لا تعدل خرائط `PLANNED` التاريخية.
- اعتماد الفئات المباشرة (295)، ومعالجة 26 فئة دلالية و111 فئة مراجعة، و14 حسابًا غير محسوم.
- تعريف قواعد الفترات المالية و29 خزنة: الحساب، طريقة الدفع، وحالة الخزنة لكل شركة.

**المخرجات المقبولة:**

- جميع الموردين النشطين من المصدر يحملون identity resolution واحدة فقط.
- company-map attestation، maps الفئات والحسابات، والفترات والخزن كلها مرتبطة بالبصمة نفسها.
- لا يوجد `FinanceSupplier` أو `FinanceVault` أو مستند مالي من نوركس في بيئة التشغيل.

**قرار البوابة:** يصدر receipt موحد `MASTER_DATA_READY` أو `NO-GO` مع أسباب محددة. لا تنشأ run للموجة 2 إلا عند `MASTER_DATA_READY`.

## الموجة 2 — الماليات كاملة ومطابقة

**الهدف:** dry-run كامل ثم staging مالي مضبوط للنطاق المعتمد.

**المدخلات والحواجز:**

- run موجة 1 الجاهزة وبصمة المصدر المطابقة.
- تحويل متحكم فيه لـ3,782 فاتورة و5,280 قيدًا؛ المورد/الفئة/الحساب/الخزنة/الفترة يجب أن تكون mapped صراحة.
- تطابق `net + VAT = gross`، وتوازن كل قيد debit = credit، والتحقق من الحالات والتواريخ والعملة.
- توقف عند المرفقات المطلوبة غير المتوفرة، القيود غير المتوازنة، أو أي معرف خارج الشركة/المستأجر.

**المخرجات المقبولة:**

- receipt لكل شركة وإجمالي موحد: accepted/rejected، counts، net/VAT/gross، debit/credit، وأسباب الرفض.
- `canStage=true` لكل شركات النطاق؛ إذا فشلت شركة واحدة تبقى الموجة كلها `NO-GO` ولا يدخل أي جزء إلى التشغيل.
- بعد staging: مطابقة مستقلة للأرصدة وعدد المستندات والضرائب والقيود لكل شركة، ثم receipt موحد `FINANCE_RECONCILED`.

**قرار البوابة:** Go يتطلب موافقة صريحة بعد receipt المطابقة؛ لا تفعيل للشركات ولا cutover تلقائي.

## الموجة 3 — HR والأصول والإغلاق

**الهدف:** ترحيل البيانات غير المالية الحساسة وإغلاق برنامج الترحيل.

**المدخلات والحواجز:**

- سياسة HR/PII معتمدة؛ نطاق الموظفين 61 ومسيرات الرواتب 21 يعالج منفصلًا عن الماليات.
- توفير payload المرفقات وmanifest/hash لها؛ الأرشيف الحالي لا يحتوي ملفات رفع الفواتير/الموظفين/الضمانات.
- الأصول والضمانات بعد توثيق الملفات فقط.
- لا ترحيل لكلمات المرور والجلسات أو الأسرار أو إعدادات backup؛ ينشأ المستخدمون والصلاحيات في بصير من جديد.

**المخرجات المقبولة:**

- receipt PII/HR، receipt مرفقات، ومطابقة العدادات للعناصر المعتمدة فقط.
- تقرير إغلاق يثبت ما رُحل، ما استُبعد، وما بقي `BLOCKED` مع السبب.
- تفعيل الشركة/cutover لا يحدث إلا بقرار Go مستقل وخطة رجوع verified backup.

## دور المراقب المستقل

- قبل كل موجة: يفحص البصمة، RLS، append-only، صلاحيات المالك، وعدادات البوابة.
- أثناءها: يراجع receipts وعدم وجود تجاوزات أو writes خارج staging.
- بعدها: يطابق العدادات والتوازنات، ويصدر `GO` أو `NO-GO` مع أدلة قابلة للتدقيق.
- لا يملك المراقب صلاحية اعتماد بيانات أو تعديلها؛ وظيفته المنع والإبلاغ فقط.
