# الميثاق الرئيسي لبناء Baseer ERP

**الحالة:** معتمد من المالك قبل البناء.  
**المنتج:** Baseer ERP - نظام ERP واحد للمالك وشركاته.  
**الأولوية:** هذه الوثيقة تحكم المبادئ والحدود الثابتة. أما ترتيب التنفيذ والحالة الحالية فيحكمهما `docs/governance/CURRENT_DELIVERY_AUTHORITY.md` وقرار المالك الأحدث.

## 1. الهدف والحدود

1. Baseer ERP هو البديل النهائي لنوركس، وليس واجهة فوقه أو تطبيقًا موازيًا دائمًا.
2. يبنى كمشروع مستقل بواجهة وخلفية وقاعدة بيانات مستقلة لكل بيئة.
3. عند الإطلاق يعمل كتطبيق واحد بقاعدة إنتاج واحدة؛ لا قاعدة بيانات لكل موديول ولا خدمات متفرقة في المرحلة الأولى.
4. نوركس والأونلاين مرجعان للقراءة والفهم والمطابقة والترحيل فقط. لا ينفذ Baseer استدعاءات تشغيلية إليهما ولا يكتب فيهما.
5. لا يبدأ تنفيذ موديول قبل اكتشاف هدفه وسير عمله والاستثناءات والصلاحيات والحسابات والتسلسلات والأثر المالي/الضريبي في النظام القديم.
6. لا يبدأ الموديول التالي قبل اكتمال الحالي واختباره ومطابقته واعتماده من المالك.

## 2. مبادئ غير قابلة للتفاوض

1. **تطبيق واحد ومصدر حقيقة واحد:** لا جداول موازية ولا cache متصفح ولا تقرير محلي يعد مصدرًا ماليًا أو تشغيليًا.
2. **الخلفية تحسب والواجهة تعرض:** يمنع في React حساب الإجماليات أو الضرائب أو الأرصدة أو النسب أو التسلسلات أو حدود الفترات.
3. **الشركة والهوية مركزيتان:** الشركة المستهدفة تستنتج في الخلفية من الجلسة وCompany Guard، لا من body متصفح قابل للتلاعب.
4. **الثيم بصري فقط:** لا يغير البيانات أو المسارات أو الصلاحيات أو سير العمل.
5. **الإلغاء محفوظ:** الحذف المالي يعني cancellation موثق يحتفظ بالمستند والserial وسجل التدقيق؛ لا محو فعلي للأثر المالي.
6. **لا Legacy handoff:** لا redirect خفي أو iframe أو API قديم واسع في موديول Baseer مكتمل.
7. **التطوير بالإثبات:** لا تعتبر قدرة مكتملة دون اختبارات عقد وتكامل وصلاحيات وعزل ومطابقة سلوك.

## 3. المعمارية المستهدفة

### 3.1 النمط

- Modular Monolith: React واحد + NestJS واحد + PostgreSQL واحدة لكل بيئة.
- النواة لا تعتمد على الموديولات. كل موديول يعتمد على النواة بعقد ضيق ومختبر.
- يسجل كل موديول manifest: الاسم، المسارات، الصلاحيات، الاعتمادات، العقود، وحالة الاكتمال.
- لا Microservices في البداية؛ فصل الموديولات يكون منطقيًا واختباريًا داخل التطبيق الواحد.

### 3.2 هيكل المشروع

```text
apps/
  api/                    Nest API
  web/                    React application shell
packages/
  core/                   identity, company, authorization, audit, dates, sequences, files
  finance/                accounting contracts and domain primitives
docs/                     ADRs, discovery, acceptance, migration evidence
migration/                read-only export, mapping, import, reconciliation
```

### 3.3 طبقات الخادم

```text
core/                     auth, tenant/company context, permissions, audit, idempotency,
                          business date, sequences, file metadata, errors
modules/                  finance | operations | people | documents | reports |
                          administration | growth | command-center
contracts/                strict DTOs, receipts, error contracts
migration/                not reachable from normal runtime API
```

كل كتابة: مصادقة → تحديد المستأجر/الشركة → صلاحية دقيقة → DTO strict → قواعد المجال → transaction + audit + idempotency → response ضيق.

### 3.4 طبقات الواجهة

```text
shell/                    navigation, session, company context, error boundaries, theme
design/                   tokens and accessible primitives
modules/                  screens and interaction only
api/                      typed clients, parsers, query keys, invalidation
```

الواجهة لا تستورد Prisma أو ledger أو calculators أو tax math. تعرض receipts خادمية فقط مع حالات loading/empty/error/retry واضحة.

## 4. البيانات المركزية والعزل

1. PostgreSQL هي قاعدة البيانات الرسمية الوحيدة لكل بيئة.
2. الهوية، الشركات، العضويات، الصلاحيات، التدقيق، الملفات، التواريخ، والتسلسلات كيانات مركزية مشتركة.
3. كل سجل يحتاج العزل يحمل tenant/company scope صريحًا.
4. العزل يطبق عبر predicates خادمية دقيقة وRLS مفروضة للجداول الحساسة.
5. لا يقبل endpoint `companyId` في body لتحديد وجهة كتابة؛ يستخلصه الحارس من سياق الطلب.
6. لا تعرض الواجهة بيانات شركة أخرى أو قائمة عضويات أوسع من صلاحية المستخدم.

## 5. الوقت والتاريخ المركزي - السعودية

1. المنطقة الافتراضية `Asia/Riyadh` باسم IANA، وليس `+03:00` مكتوبًا في الخدمات.
2. لكل شركة `businessTimezone` مركزي؛ افتراضيه الرياض.
3. `businessDate` هو `DATE` صارم `YYYY-MM-DD` ويملك شهر العملية والتقرير والتسلسل.
4. `issuedAt` للفواتير الضريبية هو `TIMESTAMPTZ` مستقل وغير قابل للتغيير بعد الإصدار.
5. `createdAt`, `updatedAt`, `cancelledAt` وaudit times لحظات تقنية مستقلة عن تاريخ العمل.
6. اختيار شهر مثل `2026-07` يعني الشهر كاملًا من 1 إلى 31 وفق تقويم الشركة.
7. حركة الفترة تبدأ من صفر. الرصيد التراكمي لا يعرض إلا بطلب صريح باسم **الرصيد حتى تاريخ**.
8. المتصفح يرسل نية (`month`, `range`, أو `businessDate`)؛ الخادم يحل الحدود ويتحقق منها.
9. يمنع في التدفقات المالية `new Date(year, month...)` و`toISOString()` لتحديد يوم العمل وحدود الوقت المبعثرة.

## 6. السياسة المالية الخاصة المعتمدة

1. Baseer ERP نظام شخصي للمالك وشركاته؛ لا تفرض عليه قيود ERP عامة غير مطلوبة.
2. الرصيد السالب في الخزائن مسموح؛ يظهر تنبيه فقط إذا لزم ولا يصبح منعًا.
3. لا يوجد إقفال تلقائي للفترات ولا منع تلقائي للعمل في الأشهر السابقة.
4. المالك يستطيع تعديل أو إلغاء عملية سابقة ضمن صلاحياته، مع احتفاظ التدقيق والأثر الصحيح.
5. كل مستند وعملية مالية يملك serial ظاهرًا وثابتًا وخادميًا لا يعاد استخدامه بعد الإلغاء أو retry أو الترحيل.
6. التسلسل يحجز ذريًا في خدمة مركزية؛ لا `count + 1` ولا suffix عشوائي غير قابل للتدقيق.
7. التقارير الإدارية الافتراضية تعرض مبلغًا شاملًا للضريبة: `115` يعرض `115`.
8. **فصل الضريبة** projection خادمي يعيد `gross=115`, `net=100`, `tax=15`، ولا يقسم المتصفح القيمة.
9. كل تدفق مالي يحدد بوضوح أثره على المستند والledger والخزنة والضريبة والتدقيق.
10. تعديل أو إلغاء المستند يعالج بعكس/إلغاء موثق داخل transaction؛ لا حذف تاريخي صامت للقيود.

## 7. الهوية والصلاحيات

1. المصادقة والجلسات مركزية، وتحمل المستأجر وإصدار الجلسة.
2. تغيير كلمة المرور أو الدور أو حالة المستخدم يبطل الجلسات السابقة.
3. الشركة النشطة ظاهرة ودائمة في shell.
4. الحراسة exact permission في route وendpoint وquery؛ إخفاء الزر وحده ليس صلاحية.
5. الأوامر الحساسة تتطلب confirmation واضحًا، audit، وidempotency عند قابلية الإعادة.
6. الاستجابات لا تسرب password/hash/path/raw permissions أو بيانات شركات أخرى.

## 8. اللغة والأرقام والجوال

1. الواجهتان العربية والإنجليزية كاملتان من catalog ترجمة مركزي.
2. الأرقام تستخدم `0-9` الإنجليزية في اللغتين، مع formatters مركزية للعملات والكسور والتواريخ.
3. اتجاه الصفحة `rtl` أو `ltr` من اللغة؛ تستخدم CSS logical properties لا left/right المتناثرة.
4. اللغة لا تغير مفاتيح البيانات أو عقود API أو الصلاحيات.
5. دعم الجوال والكمبيوتر إلزامي: أهداف لمس `44x44px` على الأقل، بديل مناسب للجداول الضيقة، keyboard navigation، قارئات شاشة، تركيز ظاهر، وتباين كاف.
6. الثيم مبني على design tokens مركزية؛ لا ألوان أو خطوط مكررة داخل الموديولات.

## 9. API والعقود

1. API versioned مثل `/api/v1/...`.
2. body/query/params تخضع لمخططات strict allowlist؛ الحقول الزائدة ترفض.
3. كل response مالي يصرح عن `source`, `period`, `asOf`, و`amountBasis` عندما ينطبق.
4. كل mutation قابل لإعادة المحاولة يستخدم `idempotencyKey` وrequest hash وreplay/conflict receipt واضح.
5. الأخطاء envelopes ثابتة، قابلة للترجمة، ولا تكشف تفاصيل داخلية.
6. لكل عقد اختبارات controller/service وtyped parser/client في الواجهة.

## 10. التدقيق والموثوقية

1. audit داخل transaction نفسها؛ فشل التدقيق يعني rollback.
2. كل تدفق كتابة حساس يملك اختبارات idempotency وconcurrency وrollback.
3. الملفات تحفظ metadata وhash وصلاحية وصول مركزية، ولا يظهر المسار الفعلي دون عقد تنزيل محمي.
4. التسلسلات والأرصدة والحجوزات الدورية تنفذ خادميًا وبقفل/معاملة مناسبة.

## 11. معايير الكود والجودة

1. TypeScript strict في الواجهة والخلفية؛ لا implicit `any`.
2. يمنع `any`, `as any`, و`as never` في كود الإنتاج والاختبارات إلا boundary خارجي موثق ومراجع.
3. ESLint وformatter وtypecheck وtests بوابات CI إلزامية.
4. لا duplicate business logic أو God service أو controller يحمل قواعد المجال.
5. لا global mutable state للحسابات أو الشركة أو الصلاحيات.
6. لا secrets في repository أو responses أو audit؛ تستخدم environment/secret manager.
7. لكل migration أو تغيير مالي/أمني: ADR، اختبارات regression، وخطة rollback.
8. يفحص CI الأسرار والاعتمادات والثغرات وحدود الموديولات قبل الدمج.

## 12. الاختبارات وبوابات القبول

1. Unit: التاريخ، التسلسل، parsing، قواعد الحساب الخالصة.
2. Service: المجال، الصلاحيات، المعاملات، الإلغاء، idempotency.
3. Controller/contract: guards، DTO strict، projections، الأخطاء.
4. Integration: PostgreSQL/RLS/concurrency/audit rollback والملفات عند الحاجة.
5. Frontend: API parsers، company switch، stale mutation، RTL/LTR، accessibility، وحالات الفشل.
6. E2E: رحلة مستخدم كاملة لكل قدرة أساسية.
7. Parity: مقارنة Baseer بنوركس على snapshot معتمدة.

لا يدمج تغيير إذا فشل typecheck أو lint أو tests أو فحص `any` أو العزل أو replay/rollback ذي الصلة أو اكتشاف حساب مالي محلي.

## 13. منهجية بناء الموديول

1. **Discovery:** الهدف، المستخدمون، flows القديمة، الاستثناءات، الصلاحيات، serials، والأثر المالي/الضريبي.
2. **Parity matrix:** ما يحفظ، ما يحسن، ما يؤجل، وما يمنع.
3. **Contract first:** APIs وreceipts وaudit قبل الواجهة.
4. **Backend first:** قواعد المجال وread models واختبارات الذرية.
5. **Native UI:** create/list/detail/edit/cancel/recovery كاملة في Baseer، بلا handoff.
6. **Validation:** RTL/mobile/a11y، errors/retry، company switch، وطباعة/تصدير خادميان عند الحاجة.
7. **Reconciliation:** مقارنة النتائج والأثر والسجل والضريبة والتسلسل مع المرجع القديم.
8. **Owner acceptance:** اعتماد المالك قبل بدء القسم التالي.

## 14. ترتيب البناء

### النواة

1. الهوية والجلسات.
2. المستأجر والشركات والعضويات.
3. الصلاحيات والأدوار.
4. shell والثيم والترجمة.
5. Business Date وBusiness Calendar.
6. audit وidempotency والتسلسلات.
7. الملفات والمرفقات.

### المالية كاملة

1. الحسابات وledger والعقود المالية.
2. لوحة المالية.
3. المبيعات اليومية.
4. الخزائن والتحويلات وكشف الحركة.
5. المصروفات الثابتة والمتغيرة والدورية.
6. الموردون والمشتريات وفواتير الموردين.
7. الالتزامات والقروض.
8. الضريبة والتقارير المالية/الضريبية.

### بقية الموديولات

العمليات، الأشخاص، المستندات، التقارير، الإدارة، ثم النمو والذكاء. مركز القيادة يبنى بعد توفر عقود المصادر الرسمية ويظل طبقة عرض وقرار فقط.

## 15. ترحيل بيانات نوركس

1. لا اتصال كتابة بالأونلاين أثناء التطوير.
2. تؤخذ snapshot قابلة للتحقق: قاعدة البيانات، المرفقات، وإعدادات الشركات.
3. تبنى خريطة دائمة `legacyId -> baseerId` لكل كيان.
4. ينقل بالترتيب: الشركات والمنطقة الزمنية، المستخدمون والأدوار والعضويات، الحسابات والخزائن والفئات والموردون، المستندات والقيود، المرفقات، ثم أرشيف التدقيق.
5. يحتفظ بالserial القديم وحالة الإلغاء. لا يعاد استخدام أي رقم.
6. `businessDate` لا يخمن؛ أي صف تاريخي ملتبس يوقف ويظهر في تقرير استثناءات.
7. تجرى بروفة import متكررة إلى staging مع مطابقة كل شركة وكل شهر: count/status, gross/net/tax, debit/credit, period movement, as-of balance, serial, cancellation, attachment hash.
8. القطع النهائي: freeze قصير في نوركس، snapshot أخيرة، import نهائي، reconciliation، موافقة المالك، ثم Baseer الكاتب الوحيد.
9. نوركس يبقى read-only مؤرشفًا وقابلًا للاستعادة؛ لا يحذف.

## 16. تعريف النجاح

يعد Baseer ERP جاهزًا للتحويل فقط عندما:

1. تكتمل الرحلات الأساسية داخل Baseer بلا Legacy handoff.
2. تتطابق التقارير والأرصدة والضريبة والتسلسلات والإلغاءات مع snapshot نوركس المعتمدة.
3. يثبت عزل الشركات والصلاحيات والبيانات بالاختبارات.
4. كل رقم وتاريخ وحساب مصدره الخلفية بعقد معلن.
5. تعمل العربية والإنجليزية وRTL/LTR والجوال والكمبيوتر بصورة كاملة.
6. تجتاز بوابات الجودة والتشغيل والترحيل ويعتمدها المالك صراحة.
