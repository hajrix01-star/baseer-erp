# سجل بناء — كتالوج الصلاحيات واعتماداته

## عقد البناء

- **المستخدم:** مالك المستأجر الذي ينشئ أو يعدل دوراً.
- **المشكلة:** الكتالوج الظاهر غير شامل أو متسق مع الأقسام الحالية، وقد تحفظ صلاحية تشغيلية بلا صلاحية مرجعية لازمة مثل قراءة الخزائن.
- **النتيجة:** جميع القدرات الحالية منظمة بالفروع، والاعتمادات اللازمة تختار وتحفظ تلقائياً.
- **خارج النطاق:** تغيير صلاحيات الأدوار النظامية أو إضافة صلاحيات لم تكن موجودة أو تعديل صلاحيات دور قائم بلا حفظ صريح من المالك.

## البوابات

| البوابة | الحالة | الدليل/القرار |
|---|---|---|
| G0 الفهم والقبول | معتمدة | الكتالوج الكامل، اعتماد ظاهر، وتطبيع خادمي قبل الحفظ؛ لا تعديل صامت للأدوار القائمة. |
| G1 المعمارية والسعة | معتمدة | أثر `ARCHITECTURAL` موثق في سجل الأثر؛ توسعة الرسم O(V+E)، بحد الطلب القائم 120 صلاحية و250 دوراً في شاشة الإدارة، بلا schema أو queue أو مكتبة. |
| G2 البيانات والعقود | معتمدة | catalog خادمي يملك الفرع والاعتمادات، والعقد ينقلها للعرض فقط؛ RolePermission لا يتغير، والحفظ الذري القائم يكتب المجموعة المطّبعة. |
| G3 التقنية والمسار المباشر | معتمدة | تعديل المصدر المالك واستخدام React/Baseer الموجودين؛ لا تبعية جديدة. المسار الأقصر والأقل مخاطرة هو توسيع الاختيار في الخدمة بدلاً من تكرار قواعد في الواجهة أو migration. |
| G4 التجربة | معتمدة | الواجهة تقرأ تسميات وفروع الخادم لكل القدرة، تعرض الاعتماد التلقائي، وتعطل إزالته أثناء الحاجة إليه؛ فحص TypeScript للويب نجح. |
| G5 التحقق | قيد المراجعة | نجحت عقود TypeScript وفحص الويب وفحص catalog واتساق التفويض واختبار محرر الدور على سطح المكتب والجوال؛ تحقق lifecycle موثق ومحدّث لكنه يحتاج بيئة API مكتملة محلياً/CI. |
