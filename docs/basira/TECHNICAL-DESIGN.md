**المرجع:** `BASIRA-AUTO v1.0` / ADR-BASIRA-002.

## 2. حدود الحل وملكيته

تبقى المنصة modular monolith بالرصة الحالية React/Nest/Prisma/PostgreSQL وعقود مشتركة. لا اعتماد جديد أو queue أو خدمة AI أخرى في الشريحة الأولى. يحسم الاختيار من ملفات الحزم وقت G3؛ لا تغير المكتبات أو النموذج لمجرد إعداد الوثيقة.

| المالك | يملك |
|---|---|
| Identity/Company context | هوية الطالب، الشركة الموثوقة، العضوية والصلاحيات |
| منصة بصيرة | سياسة تشغيل الشركة، اختيار المهارة، اعتماد الإصدار، تنسيق الاستدعاء والتكلفة والإيصالات |
| المجالات المالية/القرار/التسويق/المستندات | الحقائق والقراءات الرسمية وحزم الأدلة وصلاحية الموضوع |
| الواجهة | طلب إجراء وعرض حالة/قيمة معتمدة؛ لا حساب ميزانية أو تقرير أو قرار أهلية |
| خدمات أعمال ERP | أي إنشاء/اعتماد/ترحيل/عكس/إقفال/نشر ضمن المسارات الحالية؛ لا يمنحها router للنموذج |

مسار الرقابة المحاسبية: مستند العمل → اعتماده وترحيله بخدمة المجال → قراءة رسمية/حزمة دليل → تفسير بصيرة → عرض/مراجعة بشرية. لا توجد حافة عائدة من تفسير AI إلى دفتر الأستاذ أو حالة مستند. أي تصحيح ينتقل لإجراء العمل القائم، ولا يعدل حقيقة التفسير المحفوظة.

## 3. مسار الطلب المقترح

```text
زر سياقي: القسم + الإجراء + مرجع الموضوع + اللغة + مفتاح منع تكرار
    ↓
سياق خادمي موثوق + صلاحيات القسم والموضوع + سياسة الشركة
    ↓
registry حتمي: إجراء/نوع موضوع → adapter/مهارة معتمدة
    ↓
أهلية الإصدار والتجربة والإيقاف + حزمة أدلة خادمية صالحة
    ↓
تفسير مطابق صالح؟ ── نعم → عرض مرجعي بعد إعادة فحص صلاحيات القراءة
    ↓ لا
claim موحد → تحقق السياسة مجدداً → حجز يومي + شهري ذري
    ↓
مزود معتمد بلا أدوات حرة → تحقق JSON/المصادر/القواعد
    ↓
حفظ مشفر + تسوية usage + إيصال إصدار/سياسة + عرض النتيجة
```

الفحص قبل الاستخدام لا يستدعي النموذج. لا تصنع snapshots أو placements جديدة على GET عادي بغرض معرفة ما إذا كان الزر متاحاً؛ أعد استخدام read-only readiness ثم أنشئ/جمّد الدليل في الطلب الصريح القائم.

## 4. سياسة الشركة المقترحة

اسم منطقي مقترح `AiCompanyPolicy`، محفوظ في schema مستقلة عن السياق اللغوي. تحدد G2 الشكل النهائي مع مراعاة أعراف المشروع.

| الحقل المنطقي | النوع/القاعدة |
|---|---|
| `tenantId`, `companyId` | من سياق الخادم؛ لا ثقة في body |
| `version`, `rowVersion` | نسخة سياسة للتدقيق ونسخة للتحديث المتفائل؛ حفظ بتاريخ واضح |
| `mode` | `DISABLED` أو `ENABLED` أو `PAUSED` |
| `providerPolicy` | مرجع إلى default للمستأجر مع allowlist وبصمة موافقة للشركة على المزود والنموذج وفئة البيانات؛ لا credentials في السياسة |
| `monthlyCostLimitUsd` | مبلغ عشري نصي موجب عند التشغيل؛ لا حد مدفوع تلقائي أو مشتق من التخمين |
| `billingTimeZone` | المقترح الأول Asia/Riyadh اتساقاً مع الحارس اليومي الحالي؛ ليس timezone المتصفح |
| `scope` | أزواج مجالات/فئات بيانات/أفعال READ_EXPLAIN معتمدة؛ S3 لا تدخل لمجرد كونها «قراءة» |
| `autoEnrollStable` | يتيح الإصدارات المستقرة المطابقة للنطاق عند اجتياز شروط الإصدار؛ لا PLANNED/VALIDATED/PILOT ضمنياً |
| `pilotAllowlist` | موافقة محددة على مفاتيح تجارب وإصدارات/نطاقات معلنة؛ فارغة افتراضياً |
| `proactiveMode` | OFF في أول إصدار |
| `approvedByUserId`, `approvedAt` | من موافقة المسؤول المخوّل الفعلية |
| `changeReason`, `policyDigest` | سبب آمن وبصمة؛ لا prompt أو أسرار |

تحفظ مراجعات السياسة append-only أو بسجل تاريخ مرتبط في نفس المعاملة؛ current pointer وحيد لكل شركة وقيود unique وفهرس يبدأ بـtenant/company. لا تحذف نسخة كانت أساساً لاستهلاك أو تفعيل. يراجع جميع وصول DB عبر `inTenantTransaction` وحدود الشركة وRLS وفق النمط الموجود.

تغيير default للمستأجر لا يفوض تلقائياً إرسال بيانات الشركة إلى أي مزود/نموذج جديد. قبل كل حجز وإرسال، يطابق الخادم الملف الفعلي مع allowlist الشركة وملف capability والسعر والتقييم المعتمدين. إن خرج عن النطاق، يمنع الطلب الجديد بسبب `PROVIDER_POLICY_MISMATCH` إلى أن يختار ملفاً معتمداً أو يحدّث مسؤول مخوّل سياسة الشركة. يسجل profile digest في الإيصال وreuse، ولا يعاد تفسير من نموذج مختلف كأنه نفس الملف. تبديل مفتاح الاتصال لنفس الملف لا يغيّر موافقة نطاق البيانات ما دام المالك وحدود endpoint/الخصوصية المعتمدة لم تتغير.

### استثناءات المهارات وأولوية الإيقاف

خيار تنفيذي مقترح `AiCompanySkillOverride` بمفتاح tenant/company/skillKey، يحفظ `BLOCKED` وسببه ومن أوقفه. نطاق الإيقاف بالمفتاح عبر الإصدارات: إصدار جديد لا يعيد فتح مهارة أوقفها المسؤول.

الترتيب الحتمي: إيقاف الخادم/الإصدار → إيقاف الشركة → منع مهارة صريح → العضوية والصلاحيات → النطاق/موافقة التجربة → اعتماد الإصدار/runtime → جاهزية الدليل → السماح. يفحص الاستهلاك بعد reuse وقبل الاستدعاء؛ حجب طلب جديد بسبب الميزانية لا يمحو تفسيراً تاريخياً مسموح القراءة.

`PAUSED` يمنع الاتصال الجديد والمزامنة التي تفتح المهارات، ولا يلغي حق قراءة تفسير محفوظ من سجل التاريخ إذا بقيت صلاحية المصدر والاحتفاظ ساريتين. سحب صلاحية المصدر يمنع قراءة التفسير حتى لو كان cached. إيقاف أثناء طلب وصل للمزود لا يلغي ما أرسل فعلاً أو تكلفته؛ يسجل run والإيصال، وتمنع أي محاولة لاحقة وتراجع صلاحية عرض النتيجة.

### تفعيل داخلي بلا موافقة بشرية مختلقة

يعاد استخدام `AiSkillActivation` كدليل تشغيل. يضاف أصل واضح مثل `MANUAL` / `COMPANY_POLICY` ومرجع نسخة السياسة ودليل الإصدار؛ أسماء schema النهائية بعد G2. `approvedByUserId` الحالي إلزامي: لا تملأه بهوية system أو مستخدم عشوائي. يختار G2 عقداً يميز موافقة السياسة البشرية من تنفيذ النظام، ويحفظ الموافق التاريخي للتفعيلات القديمة دون إعادة نسبتها.

خدمة مزامنة واحدة مثل `AiCompanyPolicyService.reconcile` تعمل عند تغيير السياسة/إصدار الكتالوج، مع مصالحة محدودة عند الطلب عند الحاجة. العمليات idempotent تحت قيد company/skill/version/policy؛ لا polling في الواجهة ولا sweep غير محدود. نسخة جاهزية cached مربوطة ببصمة السياسة والكتالوج والتقييم والبوابة؛ كل استدعاء مزود يعيد فحص الحواجز الحية.

## 5. عقد جاهزية الإصدار

لكل مهارة قابلة للإتاحة التلقائية سجل release-owned يثبت:

1. handler مسجل وعقد طلب/استجابة ودليل مجال واختبارات عزل وصلاحيات.
2. بصمات skill/policy/prompt/schema/provider profile/evaluation suite.
3. تقييم OFFLINE الحالي ناجح، مع تقييم مخرجات نموذج منفصل على حالات ممثلة وعربية/إنجليزية وبيانات ناقصة وحقن تعليمات وأرقام ومراجع.
4. عتبة القبول المقترحة: صفر تسريب أو فعل ممنوع أو رقم مخترع في الحالات الحرجة، ونجاح بنيوي لكل الحالات، وقبول معنى الإجابة في `95%` على الأقل من مجموعة موثقة لا تقل عن `40` حالة لكل لغة لكل مهارة. هذه أهداف أولية تحسمها G2/G3، وليست نتائج تحققت.
5. قرار إصدار مستقل يحدد STABLE/PILOT والنطاق المعتمد، ولا يرفع PILOT إلى STABLE تلقائياً نتيجة نجاح اختبارات فقط.
6. نموذج/مزود معتمد لنفس نوع البيانات، وprice revision صالحة وبوابة تشغيل جاهزة.

تنجز هذه الأعمال في التطوير وCI/بيئة التقييم؛ لا ينفذ كل فتح شركة تقييماً مدفوعاً. يمكن تشغيل التقييم OFFLINE الخاص بالشركة تلقائياً مرة لكل بصمة تحت سياسة معتمدة. تظل فحوص البيانات والصلاحيات والتشغيل لحظية.

## 6. العقود المقترحة — تثبت في packages/contracts أولاً

هذه واجهات مقترحة وليست مسارات موجودة. يتأكد المنفذ من عدم تعارض أسمائها مع controller/routes الحاليين.

| المسار المقترح | الغرض وحدوده |
|---|---|
| `GET /administration/ai/company-policy` | قراءة السياسة الفعالة والقيم المنسقة وسبب الحالة دون أسرار |
| `PUT /administration/ai/company-policy` | تحديث مخوّل مع `expectedVersion` وidempotency؛ body للميزانية/الوضع/النطاق المسموح فقط |
| `GET /administration/ai/availability` | حالة مجالات/أفعال مسموحة لهذا المستخدم؛ لا provider call، لا تسريب أسماء موارد محجوبة |
| `POST /administration/ai/runtime/interpretations` | مدخل سياقي موحد يوجه إلى نفس handlers؛ لا prompt أو skillKey أو model يختاره العميل |

مثال طلب الأخير:

```json
{
  "moduleKey": "decision-intelligence",
  "action": "EXPLAIN_ALERT",
  "subject": { "kind": "DECISION_ALERT", "id": "opaque-id" },
  "language": "ar",
  "idempotencyKey": "client-generated-unique-key"
}
```

التحقق: enum allowlist للإجراء/نوع الموضوع، حدود أطوال، رفض المفاتيح غير المعروفة، تحقق الشركة والموضوع عبر خدمة المجال، ولا يستخدم client moduleKey كصلاحية. يرسل التسويق `ANALYZE_CAMPAIGN` مع نوع `MARKETING_CAMPAIGN`. التوجيه table-driven وليس keyword matching أو LLM.

Response مقترح باتحاد مميز: `COMPLETED` مع `NEW|REUSED` وinterpretationId/receiptId والناتج المتحقق، `IN_PROGRESS` مع runId وretryAfter، أو `UNAVAILABLE` مع reasonCode ورسالة مترجمة وإجراء آمن. لا يعاد `200` نجاحاً وهمياً لكل خطأ: أخطاء الهوية/الصلاحية/التعارض/التحقق تتبع conventions الحالية للـHTTP. لا تعرض تفاصيل موضوع غير مسموح حتى عبر reasonCode.

أسباب داخلية مقترحة: `COMPANY_DISABLED`, `SKILL_BLOCKED`, `PILOT_NOT_APPROVED`, `RELEASE_NOT_READY`, `PROVIDER_UNAVAILABLE`, `EVIDENCE_INCOMPLETE`, `BUDGET_EXHAUSTED`, `POLICY_CHANGED`, `UNSUPPORTED_ACTION`. تفصل الرسالة البشرية عن الكود التقني، ويمكن جمع الأسباب في advanced diagnostics فقط.

تبقى endpoints القرار والتسويق القديمة كواجهات توافق تمر عبر **نفس** فحص السياسة والحارس؛ يمنع مسار قديم من تجاوز السقف الشهري. لا تغير معنى `runtime/preflight` القديم بصمت؛ يوثّق deprecation أو adapter صريح واختبار توافق.

## 7. الميزانية الشهرية والدقة والتزامن

### الوضع الحالي

`AiProviderConfiguration` على المستأجر و`AiSkillActivation` لكل شركة يملكان `dailyRequestLimit` و`dailyCostLimit Decimal(18,4)`. سجل usage/الأسعار والحجز ذو تمثيل عشري دقيق. يوم الحارس الحالي Asia/Riyadh. لا يجوز وصف جمع يومي على الواجهة بأنه سقف شهري.

### قواعد البناء المقترحة

- السقف الشهري جامع لكل مهارات الشركة وكل ملفات المزود المستخدمة خلالها؛ لا نسخة ميزانية كاملة لكل مهارة.
- التحويل من LEGACY_COMPAT وسط الشهر يدخل تكاليف الشركة السابقة والالتزامات المحجوزة أو غير المؤكدة ضمن النافذة نفسها. لا يبدأ شهراً جديداً يوم التحويل؛ backfill/projection إن لزم يكون idempotent من ledger والحجوزات دون إنشاء usage مكرر. إذا كان الاستهلاك السابق أعلى من السقف الجديد يمنع الطلب الجديد، وإذا تعذرت مصالحة تاريخ مؤثر يبقى التحويل محجوباً حتى اكتمالها.
- يبقى حد المزود/المستأجر اليومي وحد المهارة اليومي حواجز إضافية أثناء الانتقال. الإتاحة الفعلية أقل الحدود المتبقية المنطبقة؛ يحسبها الخادم.
- حدود المهارة الداخلية افتراضات تشغيل versioned من ملف الإصدار، لا إعدادات يكرر المالك إدخالها؛ لا ترفع حدود قديمة صامتاً أثناء الانتقال.
- نافذة الشهر من بدايته إلى بداية التالي في timezone المحفوظة، تحفظ UTC start/end عند الحجز. يسند الطلب للفترة عند الحجز حتى لو وصلت النتيجة الشهر التالي؛ لا يصفّر counter مع كل فتح شاشة.
- الاستهلاك المحسوب = تكلفة settled + التزامات reserved غير المسواة، دون عد الحجز وتسويته مرتين. مصدره ledger، وأي projection قابلة للمصالحة معه.
- امتداد الحارس الحالي يقفل الحصص اليومية والشهرية بترتيب ثابت في جميع المسارات؛ يحجز السقفين في معاملة قصيرة واحدة قبل الاتصال، ولا يبقي transaction مفتوحة أثناء انتظار المزود.
- نسخ السياسة/التفعيل/السعر تثبت في الحجز والإيصال. يعاد فحص version وpause قبل الحجز؛ عند السباق بين pause وإرسال الشبكة يوثق الطلب المقبول مسبقاً ولا يعد بإلغاء إرسال وقع فعلاً.
- يخفض المسؤول السقف إلى أقل من الالتزامات إن أراد؛ النتيجة منع طلبات جديدة مع إظهار التجاوز القائم، لا حذف الاستهلاك أو حجز سالب. تعديل timezone لا يعيد فتح ميزانية الشهر الجاري؛ يسري من الفترة التالية.

### قرار دقة يجب حسمه في G2

قواعد alpha-build-team تطلب حد منزلتين للقيم العشرية، بينما محاسبة المزود الحالية تحتاج أجزاء السنت وحقولاً بأكثر من منزلتين. هذه **فجوة سياسة حقيقية** لا تحل بتقريب كل طلب إلى `0.00` أو تغيير schema التاريخية. المقترح: مدخل سقف شهري بشري بدقة سنتين، وحساب استهلاك بأعداد صحيحة بوحدة دقيقة ثابتة موثقة أو الحفاظ على Decimal الحالي باستثناء تقني موثق. يحسم المراجع المسار المتوافق مع قواعد المشروع؛ إذا لزم استثناء صريح فقرار المستخدم مطلوب عند التنفيذ، دون إعادة سؤاله عن هدف المنتج. لا يفترض هذا المستند أن الاستثناء ممنوح. كل تحويل وتجميع وتقريب خلفي ودقيق؛ لا `Number`/float للحساب المالي. يوضح العرض تكلفة أقل من سنت عند الحاجة ولا يوحي أن الاستخدام مجاني.

### الفشل والتكلفة غير المؤكدة

منع التكرار HTTP مختلف عن reuse: يحفظ كلاهما. يحافظ النظام على claim واحد لكل بصمة، ويرجع IN_PROGRESS للطلب المتزامن. lease الحالية للـrun والحجز مختلفة، ولذلك يجب اختبار timeout واستئناف العامل وانتهاء lease، لا الاكتفاء باختبار الضغط المتزامن السريع.

النسخة الأولى تبقي `maxRetries:0` للطلب المدفوع. انقطاع الاستجابة بعد قبول محتمل عند المزود لا يثبت أن التكلفة صفر؛ يسجل عدم اليقين ويحتفظ بحجز تحفظي/يسويه حسب العقد. لا تحرر حجوزات انتهت مع احتمال تنفيذ خارجي لمجرد انتهاء الوقت. تقترح G2 حالة تشغيلية صريحة مثل `UNKNOWN_PROVIDER_OUTCOME` ومصالحة لاحقة دون إعادة إرسال عمياء. غياب usage بعد نجاح يسوى تقديرياً تحفظياً وفق النمط القائم.

يمكن إعادة محاولة فحوص الشبكة المحلية غير المدفوعة بحد محدود. fallback لمزود آخر أو retry مدفوع يؤجل حتى إثبات عدم الازدواج والتوافق والسعر والنطاق في شريحة مستقلة؛ لا يبدل النظام المزود أو يرفع ميزانيته من تلقاء نفسه.

## 8. إعادة الاستخدام والصلاحيات والإصدارات

يحافظ `reuseKey` على tenant/company/subject/skill/version/policy/language/evidence/context/system identity/model profile/prompt. يضاف routing/data-scope policy digest عندما يغيّر المدخلات أو المسموح أو الناتج. زيادة الميزانية وحدها لا تجبر إعادة التوليد؛ تفصل `executionPolicyVersion` في الإيصال عن `contentScopeDigest` في reuse.

يفحص الخادم صلاحية المصدر والتفسير عند كل قراءة. لا تعد نتيجة موجودة تفويضاً. تغيير بيانات المصدر أو السياق أو النموذج/التعليمات/مخطط الناتج يبطل المطابقة، والنتيجة القديمة تظهر تاريخية إن سمحت السياسة، ولا تعاد كتحليل للفترة الجديدة. يحافظ على التشفير وchecksum والاحتفاظ الحالي ولا يضيف cache نصياً في browser storage.

## 9. التشغيل الاستباقي — مواصفات مرحلة لاحقة فقط

المرحلة الأولى لا عامل خلفياً لها. قبل تفعيلها لاحقاً: event type allowlist يصدر من الخادم، هوية خدمة ضيقة مرتبطة بسياسة الشركة وفئة بيانات معتمدة، recipients بصلاحيات حديثة وقت العرض، dedupe event/version + subject/evidence digest، cooldown، حد concurrency وميزانية فرعية ضمن السقف نفسه، وحالة توقف فورية. لا يستعير worker جلسة مستخدم منتهية ولا يقرأ كل الشركة لأن scope الخدمة واسع.

يفحص الحدث بقواعد حتمية قبل AI، ويعيد استخدام التفسير. تنبيه واحد عند تغير قابل للتصرف لا رسالة في كل tick. الإرسال الخارجي خارج هذه المرحلة؛ الإشعارات داخل النظام أولاً. queue جديدة تحتاج إثبات حاجة وحمل، وإلا يستعمل إطار jobs المعتمد بعد فحصه وقت تنفيذ المرحلة.

الاحتفاظ: يرث الناتج المشفر والإيصالات والسياسات مرجع الاحتفاظ الحالي للمشروع؛ لا يحذف التاريخ المالي أو audit من أجل تقليل مساحة. **قبل G1/G2 يعتمد الفريق المدد الفعلية للتفسيرات والحجوزات والمراجعات التشخيصية وسجل السياسة، ويسجل المصدر**. عند غياب سياسة رقمية يظل هذا البند مفتوحاً ولا يفترض الاحتفاظ للأبد. metadata تشغيلية جديدة قليلة المحتوى، مع cleanup محدود وقابل للاستئناف واختبار عدم حذف سجل مطلوب.

RPO لدفتر الاستهلاك الملتزم داخل قاعدة البيانات: لا فقد بسبب تعطل العملية، تثبته المعاملات والاختبارات. RPO/RTO لكارثة قاعدة البيانات يتبع خطة النسخ والاستعادة الحالية ويحتاج دليلاً منها؛ هدف 30 دقيقة للخدمة ليس شهادة استعادة قاعدة البيانات.

## 11. الرصد والتشخيص

مقاييس: eligible/blocked حسب reason آمن، new/reused/in-progress، provider latency/failure، reservation/settlement/uncertain، نسبة المهام التي تحتاج تدخل المالك، وتفاوت projection عن ledger. لا تستخدم معرفات المستخدمين/الموضوعات كـlabels عالية التنوع في metrics؛ يحتفظ audit بالمراجع المقيدة.

الأحداث الجديدة المقترحة: policy_changed، skill_auto_enrolled، skill_blocked، budget_denied، provider_outcome_uncertain. تحفظ actorKind وpolicy/release versions وrequestId، دون prompts أو مفاتيح أو صفوف ERP أو محتوى مستندات في logs. التنبيه للتشغيل بعد فشل مستمر/حالة غير مؤكدة أو قرب السقف بحسب قواعد قابلة للضبط؛ لا تنبيه متكرر عن الحالة نفسها.

## 12. شروط عدم تجاوز التصميم

لا رفع تلقائي لصلاحيات مستخدم أو الشركة، لا تشغيل مهارة بلا handler/evidence/evaluation/release، لا إلغاء suspension بإصدار جديد، لا نموذج يقرر الميزانية أو يرسم SQL، لا إخفاء فشل تحليل بتحويله إلى إجابة فارغة ناجحة. عند نقص الدليل يستخدم عرض البيانات الرسمي ورسالة واضحة كبديل بلا تكلفة.
