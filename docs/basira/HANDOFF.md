# تسليم BASIRA-AUTO إلى مبرمج أو نموذج آخر

**آخر تحديث:** 2026-09-06 · **الحالة:** مرشح التنفيذ مكتمل وقيد CI.

## 1. ما طلبه المستخدم

رأى بطاقات مهارات «مخططة/تجربة/متحقق منها» وغير قابلة للتفعيل، واعترض على تعقيد التفعيل الفردي. طلب حلاً سهلاً ديناميكياً بأقل تدخل، ثم طلب توثيق الخطط والوثيقة وخطط البناء بحيث يعرف مبرمج آخر ما يعمل.

الاتجاه المنفذ: سياسة شركة مركزية، توجيه تلقائي للمهارة المناسبة ضمن الصلاحيات والميزانية، تفاصيل فنية متقدمة، أولاً القرار والتسويق ثم استكمال المهارات. التنفيذ لا يشغّل مزوداً ولا ينشئ إنفاقاً بذاته؛ بعد النشر يمكّن مسؤول مخوّل السياسة للشركة ويحدد سقفها.

## 2. نقطة الدخول والحالة الدقيقة

ابدأ من [README](README.md). المواصفات في [PRODUCT-SPEC](PRODUCT-SPEC.md)، القرارات والعقود في [TECHNICAL-DESIGN](TECHNICAL-DESIGN.md)، والمهام واختبارات AC في [BUILD-PLAN](BUILD-PLAN.md).

ما أُنجز: خريطة عقود مستقلة، ملفات المنتج والتصميم والبناء والتسليم، ADR معتمد، سياسة شركة وعقود HTTP وحارس حجز قبل الخروج وترحيلات Prisma وجدولة تحفظية للنتائج مجهولة الحالة، وواجهة الإدارة وفحوص HTTP وE2E. الترحيلات تحققت على قاعدة اختبار معزولة؛ لا بيانات حية أو مزود إنتاجي في هذه المرحلة.

**أول مهمة تنفيذية:** BA-00. جميع BA-* في جدول الخطة TODO حتى يغيّرها منفذ بدليل. بوابات البناء ليست مغلقة لوجود وثيقة؛ راجع قسم `BASIRA-AUTO v1` في [السجل الحي](../build-governance/BUILD-GOVERNANCE.md).

## 3. قائمة البدء للمبرمج

1. اقرأ AGENTS.md والمهارات المطلوبة للمهمة؛ alpha-build-team يقود البناء وalpha-architects-team يراجع الأثر وalpha-efficient-orchestration يمنع العمل المكرر.
2. نفّذ `git status --short` و`git rev-parse HEAD`، ثم قارن ملفات ai-platform/contracts/schema/مواضع الواجهة المذكورة بالتصميم. بصمة القراءة السابقة `c37b563435057abc30e42e0646f8d03beec44555` مع تغييرات عمل سابقة؛ لا تفترض أنها نسخة clean أو إنتاجية.
3. احتفظ بعمل الآخرين. عند إعداد الحزمة كانت تغييرات في التقارير والفلاتر والتسويق وسجل البناء؛ لا تدرجها أو ترجعها ضمن برنامج بصيرة.
4. حدد التغييرات التي تبطل الدليل فقط وأعد قراءتها؛ لا تنشئ مخطط مشروع جديداً إذا كان registry كافياً.
5. اقرأ القرارات المفتوحة أدناه، وحسم التقنية بالدليل والمراجعة المستقلة قبل G0–G3. سؤال المالك فقط لقرار فعلي لا تستطيع حسمه من التفويض والسياسات.
6. ابدأ BA-01 بعد BA-00، ثم اتبع التبعيات. عند التفويض: عامل واحد للعقود/schema، وآخر لواجهة محصورة بعد ثبات العقد؛ لا مالكين لنفس الملف أو فحص.
7. سجّل النية والنتيجة والاختبارات والتراجع في السجل الحي، وحدّث حالة المهمة في الجدول وبطاقة الأثر. لا تصف اختباراً بأنه ناجح دون ناتج حقيقي.

## 4. قرارات مفتوحة يجب ألا يخمنها المبرمج

| القرار | المقترح الموثق | المالك/لحظة الحسم |
|---|---|---|
| دقة استهلاك AI مقابل قاعدة المنزلتين | سقف مستخدم بسنتين وحساب دقيق يحفظ أجزاء السنت؛ اختيار تمثيل متوافق أو استثناء صريح | ERP/المعمارية G2؛ المستخدم فقط إذا تطلب استثناءً صريحاً |
| صلاحية إدارة سياسة الشركة | شركة scope منفصل عن صلاحية إدارة مزود المستأجر | هوية/معمارية G2؛ افحص كتالوج الصلاحيات أولاً |
| قيمة الميزانية الفعلية | يحددها مسؤول الشركة مرة واحدة في الواجهة، لا رقم مفترض في migration | المسؤول عند تشغيل الشركة، لا عائق لإنشاء العقد والاختبارات |
| فترة الميزانية | شهر تقويمي Asia/Riyadh اتساقاً مع الحارس الحالي؛ timezone ثابتة للفترة | المعمارية/ERP G2 |
| اعتماد التجارب | allowlist صريح في الإعداد الأول، لا auto-enroll لكل PILOT | قرار المنتج/إصدار التجربة أثناء اعتماد النطاق، ثم مسؤول الشركة عند مشاركتها |
| أصل التفعيل | فصل منفذ SYSTEM من صاحب موافقة السياسة، والحفاظ على approvedBy التاريخي | منصة AI/البيانات G2 |
| مدد الاحتفاظ وRPO/RTO للكوارث | إعادة استخدام سياسة مثبتة؛ لا مدد دائمة مخترعة | التشغيل G1/G2، ثم دليل استعادة G8 |
| أهداف جودة النموذج والسعة | افتراضات الاختبار في التصميم؛ لا ادعاء تحققها | AI/السعة G1/G3/G6 |

هذه نقاط مراجعة هندسية مبكرة، وليست طلبات موافقة على كل شريحة. لا توقف عمل الوثائق أو الاختبارات الاصطناعية بسبب غياب ميزانية شركة حقيقية أو بيانات اعتماد إنتاجية.

## 5. أخطاء يجب تجنبها

- تغيير `PLANNED` إلى `ACTIVE` أو فتح env gates بغرض إنجاح الشاشة.
- اعتبار `VALIDATED` أو PASSED OFFLINE ضمان تشغيل وجودة نموذج.
- بناء router أو budget service أو cache يتجاوز المنصة الحالية بدلاً من تمديدها.
- رفع حد شهر كامل لكل مهارة، أو ضرب اليومي في عدد أيام الشهر واعتباره موافقة إنفاق.
- نسيان أن المزود tenant-scoped بينما السياسة والميزانية المقترحتان company-scoped.
- تجاهل توقف سابق للمهارة بعد ترقية إصدارها أو إعادة تشغيل الخدمة.
- نسبة auto-activation إلى مستخدم لم يوافق؛ SYSTEM منفذ لا موافق بشري مختلق.
- إطلاق provider call بسبب render أو polling أو مجرد توافر مهارة.
- إضافة retry مدفوع بعد timeout قبل حل charge uncertainty وleases.
- إعادة تفسير محفوظ بعد سحب صلاحية المصدر أو تغير الدليل دون فحص.
- تحويل اختيار المهارة إلى prompt عام أو فتح أدوات SQL/شبكة/نشر للنموذج.
- اعتبار قسم «الخطط» أو نجاح typecheck دليلاً على ميزانية شهرية أو عزل تحت التزامن.

## 6. سجل التسليم بعد كل شريحة

يضيف المنفذ مدخلاً في السجل الحي يحتوي:

```text
BA-ID / الهدف والحالة:
HEAD + حالة الشجرة + المسارات التي امتلكتها:
عقد API/schema/سياسة تغيرت + مرجع ADR:
ما أصبح يعمل فعلاً وما بقي:
أوامر الفحص + البيئة + النتيجة + دليل AC:
المراجع المستقل + قراره وحدوده:
مخاطر/قرار مفتوح + مالكه:
التراجع + آخر حالة بيانات/تشغيل معروفة:
المهمة التالية وسبب ترتيبها:
```

لا تكتب أسراراً أو أسماء/قيم بيانات عميل في handoff. لا حاجة لإعادة نسخ المواصفات في كل مدخل؛ اربط الملف والقسم والنسخة.
