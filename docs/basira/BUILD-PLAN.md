# خطة بناء وقبول بصيرة التلقائية

**المرجع:** `BASIRA-AUTO v1.0` · **حالة التنفيذ:** مرشح إصدار قيد CI؛ طبقت الترحيلات على قاعدة اختبار معزولة فقط، ولا مزود إنتاجي أو نشر مفعل.
**ترتيب الأولوية:** اكتمال شريحة حقيقية للقرار، ثم التسويق، ثم التوسع حسب الجاهزية. لا موعد تسليم مفترض أو نسبة إنجاز غير مقاسة.

## 1. قواعد متابعة التنفيذ

- اقرأ [المواصفات](PRODUCT-SPEC.md)، [التصميم](TECHNICAL-DESIGN.md)، [ADR](../architecture/ADR-BASIRA-002-AUTOMATIC-COMPANY-ORCHESTRATION.md)، ثم قسم `BASIRA-AUTO` في [السجل الحي](../build-governance/BUILD-GOVERNANCE.md).
- بوابات البناء تبقى في السجل الحي وحده. الحالات هنا للمهام: `TODO → IN_PROGRESS → REVIEW → DONE`، أو `BLOCKED` بسبب محدد مع مالك.
- لا يبدأ كود أو migration أو حزمة قبل أدلة ومراجعة G0–G3. هذه مراجعات فريق تقنية، ولا تتحول إلى سؤال متكرر للمالك عن أمور حسمها الطلب.
- لا تعدّ المهمة DONE دون روابط ملفات واختبارات ونسخة تحقق، ولا تخلط «خطة جاهزة» و«ميزة جاهزة».
- كل منفذ يملك الملفات المحددة فقط، ويحافظ على تغييرات الآخرين. التفويض لسؤال/شريحة مستقلة فقط؛ لا فريقين يفحصان الملفات نفسها.

## 3. BA-00 — تثبيت عقد البناء

**الملكية:** القائد يحدّث docs/basira وregistry والسجل فقط؛ قارئ العقود يحدد الفرق في ai-platform/schema/contracts دون تعديل؛ مراجعة مستقلة تسجل الاعتماد.

1. قارن HEAD والشجرة والمسارات المحددة في التصميم. أعد استخدام الأدلة المطابقة؛ لا تعاود فحص المشروع كله.
2. حسم أدوار وصلاحيات تعديل سياسة الشركة، سقف الشهر وtimezone، الاحتفاظ، تمثيل دقة الاستخدام، تمثيل أصل التفعيل الآلي وقرار pilot allowlist.
3. تثبيت احتياجات القياس والبيانات الاصطناعية وملف المزود الحالي؛ التحقق من الرصة والحزم الحالية دون ترقية تلقائية.
4. اعتماد G0–G3 تقنياً بدليل مستقل، وتحديث ADR من Proposed فقط بعد القرار الفعلي. قرارات التكلفة/المزود/البيانات التي تحتاج مالكاً فعلياً تبقى ظاهرة إلى لحظة حاجتها.

**القبول:** لا غموض في سلطة policy أو الإيقاف أو الحد الشهري أو دقة أجزاء السنت. لا secret ولا ربط إنتاجي ولا إنفاق مطلوب لإنجاز BA-00.

## 4. BA-01 — السياسة والعقود والترحيل

**الملكية:** `packages/contracts/src/ai-platform.ts`، `apps/api/prisma/schema.prisma` ومجلد migrations، و`apps/api/src/ai-platform/` وأجزاء permissions المملوكة للمنصة بعد تحديدها.

- إضافة عقد سياسة versioned وصلاحية إدارة واضحة وGET/PUT موثّقين، وتحديث role mappings وفق النمط القائم؛ company manager لا يصبح tenant provider admin.
- حفظ المراجعة والموافق الحقيقي وoverride بالمفتاح لا بالإصدار فقط؛ تحديث متفائل/idempotency/audit في معاملة واحدة.
- تكييف `AiSkillActivation.approvedByUserId` وأصل الموافقة دون اختلاق موافقات أو تغيير تاريخ قديم.
- بناء migration توسعية تحافظ على التفعيلات والإيقافات وقيود unique/RLS؛ توفير dry-run تقرير counts للحالات المعروفة والشاذة.
- إبقاء السياسة الجديدة مغلقة للشركات الجديدة حتى إعدادها؛ الشركات القديمة في وضع توافق محدود بمهاراتها الحالية دون auto-enroll أو تحويل حد يومي إلى شهري بلا قرار.

**القبول:** شركة A لا تقرأ أو تعدل سياسة B؛ تحديثان بنفس النسخة لا يسحق أحدهما الآخر؛ replay لا ينشئ مراجعة ثانية؛ وقف مهارة يطبق عبر إصداراتها؛ لا default ميزانية مدفوعة مخترع.

## 5. BA-02 — الحارس الشهري

**الملكية:** حارس الاستهلاك الحالي، عقود ونماذج reservations/usage المعنية واختبارات الخدمة. لا حسابات مالية في الواجهة.

- تطبيق قرار الدقة المعتمد وتحويلات دقيقة وحدود إدخال خلفية.
- إدخال نافذة شهرية company-wide مع الحجوزات والتسويات والتزامن ضمن الحارس الواحد؛ لا حارس موازٍ في router.
- المحافظة على الحدود اليومية وسعر المزود المراجع ورفض غياب السعر/الحد.
- معالجة unknown provider outcome وانتهاء lease واسترداد العملية قبل إدخال أي retry مدفوع.
- إضافة قراءة استخدام مجمعة ومنسقة من الخادم، وصفحات لسجل الاستخدام؛ الفهارس تتبع استعلامات الشركة والفترة، ولا scan كامل لكل طلب.

**القبول:** لا يتجاوز مجموع المهارات حد الشركة تحت التزامن، لا خصم مزدوج عند replay/reuse، لا فتح رصيد إضافي بتغيير الشهر/المزود/نسخة المهارة، لا اختفاء تكلفة محتملة بعد timeout.

## 6. BA-03 — الأهلية والتوجيه

**الملكية:** ai-skills وruntime وservice داخل ai-platform وcontract وحدات الاختبار؛ تسجيل Nest بنفس النمط الحالي.

- تعريف جدول إجراءات مسموحة إلى handler، وتوثيق عدم وجود route عندما لا يوجد implementation.
- تثبيت سجل اعتماد/manifest أولي للقرار والتسويق: reuse لدليل PILOT سابق فقط إذا تطابقت نسخ التنفيذ والمزود والتقييم وثبت مصدر الدليل، وإلا يستكمل تقييم الجودة والاعتماد قبل اتصال حي. BA-08 توسعة stable auto-enroll لاحقاً وليست أول إنشاء لدليل الإصدار.
- تنفيذ eligibility بترتيب الإيقاف/الصلاحيات/نطاق البيانات/التجربة/release/runtime/readiness.
- مصالحة تفعيل المهارة داخلياً عند تغير policy/release مع دليل أصلها؛ OFFLINE يعاد مرة للبصمة لا لكل طلب.
- إضافة unified endpoint مع adapters توافق للـendpoints القديمة، وربط الجميع بنفس الحارس والسياسة.
- حفظ policy/routing versions في الإيصال ومفتاح reuse المؤثر في الناتج؛ تغيير الميزانية فقط لا يهدر تفسيرات سليمة.

**القبول:** لا تعتمد الواجهة skillKey أو model ولا تنشئ server gate؛ PLANNED/VALIDATED لا تعمل؛ التجربة تحتاج موافقة مطابقة؛ تعليق المستخدم لا يزول عند reconcile أو نشر إصدار.

## 7. BA-04 — شريحة قرار كاملة G4/G5

**الملكية:** لوحة إدارة بصيرة + موضع شرح التنبيه، dictionaries ومكونات Baseer المستخدمة فقط؛ خدمة القرار تحت مالك مستقل عند الحاجة.

- تصميم واعتماد G4 باستخدام المكونات الموجودة: `baseer-card.tsx`، `baseer-button.tsx`، `baseer-form-dialog.tsx`، `baseer-form-fields.tsx`، `baseer-async-state.tsx`، `baseer-company-read-query.tsx`، `number-format.ts` و`administration-copy.ts`.
- يطبق المنفذ مهارة Baseer UI وemil-design-eng عند تصميم الواجهة الفعلي؛ لا مكتبة جديدة ضمن الخطة الحالية. أي مكتبة مقترحة تفتح G3 وتستدعي pick-ui-library.
- زيارة واحدة لإعداد الشركة، الاستفادة من مزود المستأجر، حد شهري واضح، وموافقة التجارب في نفس الرحلة إذا انطبقت.
- زر «اشرح التنبيه» يرسل typed intent؛ يعرض source/period/limitations ومؤشر محفوظ/جديد/قيد التنفيذ.
- إبقاء تفاصيل المهارات في advanced؛ لا مطلب فحص/ميزانية/تفعيل لكل مهارة للمستخدم العادي.

**القبول:** رحلة عربية وإنجليزية بعرض 360px وسطح مكتب، لوحة مفاتيح، حالات فارغة/خطأ/تعطيل. opening/filtering/reload ينتج صفر provider calls. اختبار أول شرح ثم reuse ثم تغيير الدليل. لا توسع BA-06 قبل قبول هذه الشريحة.

## 8. BA-05 — إثبات السعة G6

ينشئ مهندس السعة fixtures آمنة ويتبع ملف G1 في التصميم. يثبت البيئة والنسخة وحجم البيانات والأوامر وp50/p95 ومعدل الخطأ والتكلفة المتوقعة وحدود القياس. يبدأ بمزود stub حتمي؛ جودة النموذج تقاس منفصلة ضمن اعتماد الإصدار.

يقيس 20 طلباً للموضوع نفسه، مواضيع مختلفة بنفس الشركة، شركتين، وصول السقف تحت التزامن، pause أثناء الحجز، نهاية شهر، انتهاء leases، وتعطل بعد إرسال الطلب وقبل التسوية. no-double-charge والتفويض اختبارات قبول قطعية؛ أهداف التأخير تقديرية يجب تفسير أي إخفاق فيها. لا اختبار حمل على إنتاج أو بيئة مشتركة دون تفويض مناسب.

## 9. BA-06 وBA-07 — التسويق ثم الإصدار الأول

BA-06 يربط تحليل الحملة بالـrouter نفسه، ويحفظ quality gates ومصدر المبيعات الرسمي وفجوات الإنفاق وحظر السببية. لا موصل Google جديد ولا تغيير OAuth؛ يستهلك الدليل المعتمد القائم فقط. يختبر طلبين من القسمين يتنافسان على ميزانية الشركة نفسها.

BA-07 ينجز الانتقال والرصد والرسائل والتشغيل وrollbacks التالية، ثم يقدّم مرشحاً محدد النسخة إلى فريق ألفا للتسليم. حالة الوثائق الحالية ليست مرشح إصدار.

## 11. أوامر التحقق

الأوامر التالية موجودة عند فحص package.json بتاريخ الحزمة، **لم تُشغّل في جلسة التخطيط**. يتحقق المنفذ من scripts والـprerequisites بعد تغير النسخة. يبني العقود قبل API/web عند تغيرها؛ لا يعيد البناء لكل verifier إذا كان dist المطابق جاهزاً ويمكن استخدام verifier مباشرة وفق script.

```text

npm run check --workspace @baseer-erp/api
npm run check --workspace @baseer-erp/web
npm run build --workspace @baseer-erp/contracts
npm run build --workspace @baseer-erp/api
npm run build --workspace @baseer-erp/web
npm run check:architecture
npm run check:nest-registration
npm run check:permissions
npm run check:authorization-consistency
npm run check:ai-gate-b
npm run verify:basira-skill-evaluations
npm run verify:basira-analysis-readiness
npm run verify:basira-provider-capabilities
npm run verify:basira-consumption-guard
npm run check:web-api-transport
npm run check:web-localization
npm run check:web-numeric-policy
npm run check:web-financial-boundaries
npm run check:ui-governance-registers
```

فحوص DB/HTTP التالية تتطلب قراءة runner وضبط قاعدة اختبار معزولة وترحيل schema الصحيح وتشغيل API حيث يلزم؛ لا توجه إلى إنتاج أو تعتمد `.env` دون التحقق من هدفه:

```text
npm run verify:ai-gate-b-db
npm run verify:ai-gate-b-http
npm run verify:basira-interpretation-foundation
npm run verify:decision-intelligence-foundation
```

تضاف اختبارات AC الجديدة إلى runner المشروع المناسب؛ لا تدّع أن verifiers الحالية تغطي سياسة/شهرية/router لم تبن بعد. اختبارات E2E تغطي القرار والتسويق والإعداد على بيانات اختبار مصرح بها. فحوص UI الإضافية وCI acceptance الكاملة تحدد من CI وقواعد المستودع في G8. لا يعوّض typecheck فحص السباقات أو الميزانية أو صلاحية المصدر.

## 12. الانتقال والتوافق والتراجع

1. **الجرد:** dry-run مصنف للشركات والتفعيلات النشطة/الموقوفة/المنتهية وتقييماتها وحدودها؛ totals فقط في docs، دون بيانات أو أسرار عملاء.
2. **Expand:** schema جديدة قابلة للتعايش، وقراءة السياسة الجديدة خلف rollout setting خادمي موثق. لا feature flag من المتصفح ولا كتابة status بالقوة.
3. **حفظ الماضي:** تظل suspended/expired غير فعالة؛ كل suspension قديم يترجم إلى override محافظ بالمفتاح حتى مراجعة سبب صلاحية أضيق موثقة. لا نشتق موافقة شهرية من حاصل `daily × 30`.
4. **وضع الشركات القائمة:** تستمر التفعيلات القديمة ضمن حدودها القائمة في LEGACY_COMPAT منطقي مع auto-enroll مغلق. يعرض إعداد الانتقال مرة واحدة عند رغبة المسؤول بتشغيل السياسة الجديدة، وبميزانية شهرية صريحة. لا انقطاع غير معلن ولا توسيع تلقائي.
5. **Shadow:** حساب أهلية السياسة الجديدة للمقارنة دون provider أو تفعيل إضافي، وتفسير الفروق بين قرارات المسار القديم والجديد.
6. **Pilot معزول ثم شركة مخولة:** يراجع الفريق النتائج ويربط نسخة migration/manifest/evaluation، مع موافقة التشغيل الفعلية المطلوبة في سياق التنفيذ. برنامج الوثائق لا يختار شركة إنتاجية نيابة عن المالك.
7. **Cutover:** للمتحولة فقط تمر كل endpoints عبر السياسة الشهرية. تجرى مصالحة idempotent لاستهلاك الشركة السابق وكل الحجوزات/الالتزامات غير المؤكدة داخل الشهر الجاري من ledger ومصادر الحجز؛ لا يبدأ السقف من الصفر يوم الانتقال ولا يعاد إدخال usage. إن تجاوز السابق الميزانية الجديدة يمنع الجديد؛ نقص سجل مؤثر يمنع التحويل حتى مصالحة موثقة. التحويل ذري مع الحارس كي لا تسقط طلبات أثناء جرد الاستهلاك؛ لا كتابة مزدوجة مستقلة تتعارض فيها المصادر.
8. **Rollback:** استعادة الواجهة/التوجيه السابق مع إبقاء حارس السياسة والشهرية فعالاً. إذا كان الخادم القديم لا يفهم هذه الحواجز يوقف AI للشركات المحولة؛ لا يعود LEGACY_COMPAT تلقائياً ليتهرب من سقف الشهر.
9. **Contract لاحق:** لا إسقاط أعمدة/جداول أو حذف تفعيلات/إيصالات إلا بعد نافذة توافق وقرار ترحيل مستقل. لا rollback تدميري لـledger.

معايير توقف التوسعة: أي خرق عزل، إعادة تفعيل suspension، ازدواج تكلفة، تجاوز سقف، نتيجة مالية مختلقة، أو غموض تكلفة متكرر بلا مصالحة. أعطال الأداء تعالج وفق SLO المقاس؛ لا يخفى إخفاقها بعرض نجاح وهمي.

## 13. استكمال القدرات التالية

BA-08 يوسّع release manifest وتقييمات الجودة الأولية المثبتة في BA-03/07 لتشمل الإصدارات المستقرة الجديدة، ويضيف contract scope-diff، ثم يثبت إدراج قدرة مستقرة دون إعداد يدوي جديد وفشل الإدراج عند توسع النطاق أو إيقاف صريح. لا يرفع تجارب القرار والتسويق إلى STABLE دون قرار إصدار مستقل.

كل BA-09* شريحة مستقلة تشمل: مالك مصدر البيانات، حزمة أدلة محدودة ومأذونة، handler وعقد ناتج، capabilities، provider profile وتكلفة، تقييم جودة، UI سياقي، اختبارات سلبية، وقرار إصدار. لا يفتح المفتاح في ai-skills قبل اكتمال هذه الأدلة. BA-09B يراجع ERP قبل البيانات؛ BA-09D يحسم ملفات/رؤية/الاحتفاظ والخصوصية وموافقة نطاق S3. قد ينفذ دليل الإدارة بقراءة حتمية بلا نموذج إذا حققت الحاجة.

BA-10 لا يبدأ من scheduler فقط: يبدأ بعقد أحداث وهوية خدمة ومتلقي مخوّل وdedupe وcooldown وحد تكلفة واختبار pause وreplay، ثم يقرر الفريق الحاجة لعامل/queue. لا نشر Google أو مراسلة خارجية ضمنها. لا retry/fallback مدفوع ضمن الإصدار الأول؛ إدخاله تغيير مستقل يعيد مراجعة BA-02 وG2/G3/G5/G6.
