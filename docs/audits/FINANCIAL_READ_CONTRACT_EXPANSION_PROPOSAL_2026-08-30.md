# مقترح توسيع عقد القراءة المالية — سياسة العرض الضريبي

**الحالة:** مقترح معتمد بانتظار التنفيذ المرحلي.
**قرار المالك:** 30 أغسطس 2026.

## السياسة الملزمة

1. كل واجهة تشغيلية أو إدارية أو تحليلية خارج التقارير تعرض المبالغ **شاملة ضريبة القيمة المضافة** فقط.
2. لا يظهر زر لاختيار الصافي أو فصل الضريبة في هذه الواجهات.
3. تقرير الربح والخسارة والتقارير القائمة لا تتغير حسابياً أو وظيفياً: يظل عرضها الافتراضي شاملاً الضريبة، ويستمر زر فصل الضريبة الحالي فيها فقط.
4. لا يصبح الصافي قيمة افتراضية في أي واجهة جديدة. ولا يظهر عند نقص المصدر بدلاً من قيمة gross؛ تعرض الواجهة `—` وحالة الجودة.

## شكل العقد المستهدف

لا ينشأ DTO مالي ضخم موحد. ينشأ غلاف اختياري versioned في `packages/contracts` يرافق receipt المتخصص:

```text
financialRead:
  contractVersion
  subject                 # SALES | CASH_MOVEMENT | PURCHASE_SPEND | MIXED_ANALYTICS
  defaultTaxView          # VAT_INCLUDED
  allowedTaxViews         # [VAT_INCLUDED] خارج التقارير
  authority
  quality
  currencyScope
  presentationPolicy      # SERVER_FORMATTED
```

ويكون الاستثناء محصوراً في التقرير القائم:

```text
profit-and-loss / existing reports:
  defaultTaxView = VAT_INCLUDED
  allowedTaxViews = [VAT_INCLUDED, VAT_SEPARATED]
  preserveExistingReportSemantics = true
```

يبقى `coverage` التفصيلي، والمطابقة، وحقول الرسم وpayload لكل قسم داخل عقده التخصصي؛ لأن تغطية المبيعات ليست تغطية حركة النقد أو التسويق.

## ما لا يتغير

- endpoint وخيارات `vatInclusive` الحالية لتقرير الأداء النقدي والتقارير الرسمية.
- منطق الربح والخسارة، القيود المختومة، revision/report runs، وأدلة التقرير.
- عقود snapshots التاريخية لموجز المالك؛ تتلقى adapter توافق قبل أي إلزام للعقد الجديد.

## موجات التنفيذ

| الموجة | النطاق | التغيير | بوابة الخروج |
| --- | --- | --- | --- |
| 0 | النواة | إضافة primitives و`financialRead` اختياري بلا حذف أو إعادة تسمية | بناء العقود وتحليل توافق receipts القديمة |
| 1 | التقارير | إرسال display خادمي لـ debit/credit وحذف تحويل `money.raw` في الواجهة | HTTP + UI: لا `Number`/`formatMoney` على المال الخام |
| 2 | التسويق ومركز القيادة | receipt متخصص: currency/basis/authority/quality/display؛ استبدال API types المحلية | gross-only في العرض وحارس ساكن موسع |
| 3 | المبيعات والتشغيل وحركة المالك | اعتماد الأنواع المشتركة عبر adapters بلا تغيير UX | schema golden + company isolation + incomplete=`—` |
| 4 | موجز المالك والتاريخ | adapter للـsnapshots القديمة ثم إلزام receipts الجديدة | parse للقديم والجديد وعدم دمج العملات |
| 5 | حوكمة الإطلاق | توسيع static guard وHTTP/RLS لكل surface | لا واجهة غير تقريرية تسمح بفصل الضريبة |

## المخاطر وضوابطها

| الخطر | الضابط |
| --- | --- |
| خلط المبيعات بحركة النقد | `subject` وauthority مميزان؛ لا يرث cash movement مطابقة المبيعات |
| كسر التقارير الحالية | التقارير مستثناة وظيفياً؛ adapter لا replacement |
| إلغاء معنى `vatInclusive=false` في التقرير | يبقى الخيار الحالي داخل التقرير فقط |
| كسر snapshots تاريخية | `financialRead` اختياري أولاً مع compatibility state |
| إعادة حساب الواجهة | حارس شامل واختبارات عرض حرفي للقيم الخادمية |

## معيار القبول النهائي

- كل واجهة غير تقريرية تعلن وتعرض `VAT_INCLUDED` فقط.
- الربح والخسارة والتقارير القائمة تحتفظ بزر فصل الضريبة ومنطقها الحالي دون اختلاف نتيجة.
- كل مبلغ ظاهر خارج حقول الإدخال صادر كـserver-formatted display.
- الحالات الناقصة لا تصبح صفراً.
- اختبارات API/RLS/واجهة تثبت العزل بين الشركات والضريبة والتوافق الخلفي.
