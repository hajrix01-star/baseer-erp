# BASEER ERP — مركز المستندات والربط المالي

**English name:** `Inbound Evidence & Payment Hub`
**Date:** 2026-08-15
**Status:** Owner-approved scope decision; queued behind the active Daily Sales Closing scope. This is not an implementation or an enabled integration.

`docs/governance/FINANCIAL_AND_FACTUAL_SOURCE_OF_TRUTH_POLICY_2026-08-15.md` applies: inbound evidence and a payment order are not financial truth. A money amount becomes reportable only after the authorized workflow creates a sealed journal effect or documented reversal.

## 1. النتيجة المطلوبة

يوفر هذا المجال مساراً واحداً وآمناً لاستقبال مستندات العمل وتحويل الدليل المالي إلى **طلب مراجعة** يمكن ربطه بعملية مالية صحيحة في BASEER ERP. وهو لا يستورد بريدًا أو مستندات بلا حدود، ولا ينشئ قيدًا أو حركة صرف من تلقاء نفسه.

المصادر المخططة:

1. البريد المركزي للمالك، بما في ذلك الرسائل المحولة من عناوين شركاته.
2. صور وملفات الإيصالات الواردة حالياً عبر Telegram.
3. رسائل SMS البنكية مستقبلاً، بعد قرار موصل مستقل وإثبات صلاحية القناة.

## 2. قسمان في واجهة واحدة

### أ. البريد الوارد للشركات

يعرض فقط رسائل العمل بعد تصنيفها، مع حفظ:

- المستلم الأصلي، عنوان التحويل إن وجد، المرسل، وقت الاستلام، مسار التسليم، والمرفقات.
- الشركة المرشحة، أساس الربط، درجة الثقة، وحالة المراجعة.
- هل هي فاتورة، إشعار تحويل، كشف تسوية، عقد، تقرير، أو رسالة لا تصلح كدليل مالي.

لا يكفي ظهور الرسالة في البريد المركزي لتحديد الشركة. تعتمد المطابقة على المستلم الأصلي أو معرف شركة/حساب موثوق أو مراجعة بشرية. الرسائل الشخصية أو غير المتعلقة بالعمل تبقى خارج سجل العمل.
### قرار الربط البريدي المعتمد

- البريد المركزي الرسمي هو **Gmail** ويرتبط به BASEER ERP عبر Gmail API خادمي وبصلاحية قراءة فقط بعد بوابة موصل مستقلة.
- قد تصل رسائل شركات إلى Gmail مباشرة أو بعد تحويلها من عنوان/صندوق آخر. تحفظ الرسالة المستلم الأصلي ومسار الوصول بدلاً من افتراض الشركة من الصندوق الذي انتهت إليه.
- إذا كان Outlook مصدراً للتحويل، يفحص مجلد `Junk Email` منفصلاً عند اعتماده، لأن الرسائل غير المرغوب فيها قد لا تصل إلى Gmail.
- يحفظ النظام لكل حدث: `messageId` الثابت، `threadId` عند توفره، المرسل، المستلم الأصلي، المستلم النهائي، مسار التسليم، وقت الاستلام، المرفقات وحالة المعالجة.
- تمنع الرسالة نفسها من الظهور مرتين في Gmail وOutlook باستخدام معرف الرسالة أولاً، ثم مراجع العمل الموثقة مثل رقم الفاتورة أو الطلب أو الاشتراك أو الحساب.
- إذا لم تثبت الرؤوس أو البيانات المستلم الأصلي، تكون الحالة `UNKNOWN_ROUTE` ولا يختلق النظام شركة أو مسار تحويل.

واجهة غرفة التحكم أو البريد لا تستدعي Gmail مباشرة؛ فهي تقرأ سجلات ورسائل مستوردة ومدققة من الباكند مع حداثة المصدر وحالة الاكتمال. لا يخزن BASEER رمز Gmail أو رؤوس OAuth أو محتوى البريد الخام في المتصفح أو السجل التشغيلي.

### ب. طلبات القيود والصرف

يتحول الإيصال أو رسالة البنك أو المرفق المالي إلى `طلب مستند مالي`، لا إلى قيد مباشر. يربط الطلب بالدليل الأصلي وبالبيانات المستخرجة والمراجعة، ثم يمكنه إنشاء مسودة أمر صرف أو سند صرف وفق حالته.

## 3. سجل المطابقة الموثوق

يتطلب كل ربط تلقائي سجلات رئيسية تابعة للشركة نفسها:

| السجل | الغرض |
| --- | --- |
| حساب بنكي موثوق | يحدد الشركة ووظيفة الحساب: تشغيلي، منصات، رواتب، أو وظيفة يحددها المالك. |
| خزينة BASEER | الوجهة المحاسبية المعتمدة عند تأكيد الدفع أو التحصيل. |
| بند مصروف دوري | المورد والتصنيف والحساب ورقم الخدمة/الفاتورة، مثل اشتراك الكهرباء. |
| مورد أو ذمة | يستخدم عندما يتعلق الدليل بفاتورة مورد أو سداد جزئي/كامل. |
| قاعدة مطابقة موثوقة | قاعدة صريحة ومراجعة، مثل رقم خدمة ثابت لبند كهرباء ARZ؛ لا تنشأ تلقائياً من اختيار واحد. |

تحفظ أرقام الحسابات والآيبان وأرقام الخدمات بأقل قدر لازم للمطابقة: قيمة محمية خادمياً ومفتاح بحث مضبوط وآخر أرقام للعرض المموه. لا ترسل الأرقام الكاملة إلى الواجهة أو إلى مزود الذكاء.

### مثال معتمد

```text
إيصال خصم من حساب ARZ التشغيلي
        + رقم خدمة 555
        ↓
ARZ + بند كهرباء ARZ + الدليل البنكي
        ↓
مسودة طلب صرف قابلة للمراجعة
```

إذا غاب التطابق أو تعارض، يختار المراجع الشركة أولاً، ثم يرى البنود الدورية **النشطة لتلك الشركة فقط**. يختار مثلاً `ARZ → كهرباء`، ويحفظ النظام أن الربط يدوي وسبب ذلك. خيار `حفظ كقاعدة موثوقة مستقبلًا` مستقل ويتطلب تأكيداً وصلاحية مناسبة.

## 4. أوامر الصرف وسندات الصرف

### أمر صرف

هو طلب دفع قبل التنفيذ. حالاته:

`DRAFT → SUBMITTED → APPROVED | REJECTED | CANCELLED`

لا ينشئ أمر الصرف قيداً أو يغير رصيد خزينة. يحمل الشركة، المستفيد/المورد، البند أو الذمة، المبلغ، الحساب/الخزينة المقترحة، الدليل، وتاريخ الأعمال.

### سند صرف

هو إثبات الدفع بعد وجود دليل وتنفيذ معتمد. حالاته:

`DRAFT → READY_FOR_POSTING → POSTED → REVERSED`

ينشئه المحرك المالي فقط داخل فترة مفتوحة وبـ idempotency وتدقيق كامل:

- سداد ذمة مورد: `مدين ذمم الموردين / دائن الخزينة`.
- مصروف مدفوع مباشرة: `مدين حساب المصروف / دائن الخزينة` وفق وثيقة المصروف المعتمدة.

يمكن ربط سند صرف بأمر صرف قائم أو بدليل بنكي وصل بعد السداد. لا يعني وجود الإيصال أنه معتمد، ولا ينشأ سند أو قيد تلقائياً من Telegram أو البريد أو SMS أو الذكاء.

## 5. الذكاء المركزي وOCR للمرفقات

كل مرفق وارد من Gmail أو Telegram أو SMS مدعوم (صورة، PDF أو مستند) يدخل أولاً إلى مسار ملف محكوم، ثم إلى OCR لاستخراج النص، ثم إلى مهارة الذكاء المركزية لفهم النص واقتراح بيانات منظمة. لا يثق النظام في OCR أو الذكاء كمصدر مالي؛ النتيجة دائماً مسودة مراجعة بشرية.

يستخرج المسار اقتراحات محدودة: نوع المستند، المبلغ، التاريخ، مرجع بنك، رقم خدمة/فاتورة، مورد، حساب ممّوه وشركة محتملة. ويحفظ النص المستخرج ونتيجة التحليل كبصمة/نسخة مرتبطة بالدليل ونسخة OCR والمهارة والمزود ودرجة الثقة، حتى يمكن مراجعة سبب الاقتراح أو إعادة تشغيله بعد تحسن المهارة.

وهو يلتزم بـ:

- CompanyContext وقراءة الأدلة المرخصة فقط.
- فحص نوع الملف والحجم وبصمة المحتوى قبل OCR؛ المرفق غير المدعوم أو المشبوه يبقى `NEEDS_REVIEW` ولا يرسل للمزود.
- إرسال بيانات مصغرة ومموهة للمزود الخارجي؛ لا أسرار أو حسابات كاملة أو قيود/عملاء خام.
- إعادة النتيجة مع الدليل ودرجة الثقة ونسخة OCR والمهارة/المزود، لا كقرار ملزم.
- منع إنشاء أو اعتماد أو صرف أو ترحيل أي قيد من OCR أو الذكاء.

## 6. الضوابط الإلزامية

1. فصل الصلاحيات: منشئ الطلب لا يعتمد طلبه؛ والتنفيذ المالي لا يحدث من شاشة البريد.
2. كل تغيير أو ربط يدوي أو اعتماد أو إلغاء يحمل actor ووقت وسبب وارتباطاً بالدليل.
3. منع التكرار بمفتاح الدليل/بصمة الملف، الحساب المموه، مرجع البنك، التاريخ، المبلغ، والعملية المالية المرتبطة.
4. المرفقات تستخدم `FileMetadata` وإعادة تفويض عند العرض أو التنزيل؛ لا رابط تخزين عام.
5. أي دليل غير مكتمل أو شركة غير مؤكدة يبقى `NEEDS_REVIEW`، وليس مبلغاً صفرياً أو قيداً معلقاً صامتاً.
6. العكس يتم بعكس المستند والقيد، لا بتعديل سجل مالي مرحل.

## 7. خارج النطاق

- مطابقة كشف البنك الشاملة أو استيراد كشف الحساب البنكي؛ هذا مستبعد بقرار المالك.
- تنفيذ تحويلات بنكية أو دفع تلقائي عبر أي بنك أو منصة.
- قراءة كل البريد أو تخزين الرسائل الشخصية.
- اعتماد ذكي أو إنشاء قيد/سند صرف تلقائي.
- نقل بيانات أو تكاملات أو أسرار من Noorix أو Hajri Business Control.

## 8. ترتيب البناء قبل أي واجهة

### Gate E1 — الأدلة والسجلات الموثوقة

- نماذج المستند الوارد، المصدر، المرفق، الحالة، الشركة المرشحة، الدليل ودرجة الثقة.
- ملفات محكومة، سجل الحسابات البنكية/وظائفها، أرقام الخدمات، وقواعد الربط اليدوي المراجعة.
- RLS، CompanyContext، audit، idempotency، واختبارات العزل والتكرار والمرفقات.

### Gate E2 — أمر الصرف وسند الصرف

- أوامر صرف وحالات اعتماد منفصلة.
- سندات صرف مربوطة بوثيقة مصروف أو ذمة مورد وبالـ Journal sealed.
- اختبار الفترة المفتوحة، التزامن، الاعتماد، الإلغاء والعكس؛ لا endpoint يدوي للقيد.

### Gate E3 — موصلات الاستلام والذكاء

- موصل Gmail API خادمي read-only يحدد المستلم الأصلي ومسار التحويل؛ وموصل Outlook/Junk منفصل فقط إذا اعتمده المالك. لا تعتمد الواجهة على لقطة محلية أو قراءة مباشرة من المتصفح.
- Telegram ثم SMS، كل قناة بقرار موصل مستقل وحماية أسرار وreceipt للمعالجة.
- OCR محكوم للصور وPDF والمرفقات: فحص ملف ثم استخراج نص ثم تحليل مركزي إلى مسودة قابلة للمراجعة؛ لا استيراد تلقائي ولا ترحيل تلقائي.
- AI Gateway بأدوات تحليل محدودة ومسار مراجعة بشري.

### Gate E4 — الواجهة

- Inbox، صفحة مراجعة دليل، اختيار يدوي للشركة والبند، أمر صرف، سند صرف، وحالات فشل/نقص الدليل.
- واجهة ثنائية اللغة وRTL/LTR ولا تعرض أسراراً أو أرقام حساب كاملة.

## 9. علاقة القرار بخارطة البناء

يبقى **Daily Sales Closing** النطاق النشط ولا يتغير ترتيب Marketing Performance أو AI Assistant بهذا القرار. يبدأ هذا المجال بعد اعتماد Daily Sales Closing ثم إغلاق Marketing Gate A، إلا إذا سجّل المالك استثناء أولوية محدداً. عند بدء تنفيذه يبدأ بـ E1 وE2 في الباكند قبل أي موصل أو واجهة.

## قرار المالك

اعتمد المالك أن يضم BASEER ERP البريد الوارد المخصص للعمل، وأدلة Telegram ثم SMS، وربط الحسابات البنكية والبنود الدورية، والربط اليدوي، وأوامر الصرف وسندات الصرف وفق هذا النطاق. لا يُفسر الاعتماد كتصريح لتفعيل البريد أو Telegram أو SMS أو الذكاء أو أي صرف فعلي قبل اجتياز البوابات أعلاه.
