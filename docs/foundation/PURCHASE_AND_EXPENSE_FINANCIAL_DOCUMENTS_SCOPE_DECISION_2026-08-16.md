# قرار نطاق مستندات المشتريات والمصروفات — 2026-08-16

**الحالة:** نطاق التنفيذ النشط — Gate A مكتمل، يبدأ Gate B بالعقود ثم قاعدة البيانات والخادم.  
**المصدر المرجعي:** فحص مصدر Noorix المحلي، ولا سيما شاشة دفعات المشتريات ودورة الفاتورة الصادرة للمورد، مع سجل الاكتشاف السابق `../migration/NOORIX_PURCHASES_EXPENSES_AND_SUPPLIER_INVOICES_DISCOVERY_2026-08-15.md`.

## الهدف

تسجيل مستند مالي حقيقي للمشتريات أو المصروفات؛ وليس صورة إيصال أو جدولاً محلياً. كل مستند محفوظ يملك رقماً داخلياً، شركة وسياق صلاحية، تاريخ عمل، مورد وتصنيف، ضريبة محسوبة خادمياً، طريقة تسوية، أثر Journal موثق، وإيصال عملية قابل للمراجعة.

## ما نأخذه من نوركس

1. إدخال مفرد سريع للمورد والفئة وتاريخ المستند ورقم فاتورة المورد والمبلغ والضريبة وطريقة السداد والملاحظات.
2. إدخال جماعي لاحق: صفوف فواتير مستقلة تشترك فقط في جلسة الإدخال؛ لا تتحول إلى سجل مالي موازٍ.
3. سجل مستندات بفلاتر فترة ومورد وحالة، وفتح رقم المستند لتفاصيله؛ لا عمود إجراءات مزدحم.
4. تصحيح داخل الفترة المفتوحة، وإلغاء محاسبي واضح لا حذف.
5. منع تكرار فاتورة المورد بعد تطبيع رقمها (مسافات، حالة الأحرف، الأرقام العربية/الفارسية/اللاتينية).

## حدود بصير في الشريحة الأولى

- الأنواع: `PURCHASE` و`EXPENSE` فقط. الرواتب والسلف وشؤون الموظفين والمخزون وطلبات الشراء خارج النطاق.
- التسوية: **مدفوع** عبر خزينة واحدة أو أكثر، أو **مستحق للمورد** عبر سجل الاستحقاقات الحالي. لا تسوية بنكية ولا صرف آلي.
- الضريبة: حساب خادمي وحفظ لقطة net/VAT/gross ونسبة المعاملة؛ لا يعاد تفسير مستند قديم عند تغيير إعداد الشركة.
- الدليل/المرفق: مرجع metadata فقط عند توفره؛ رفع الملفات وOCR والبريد وTelegram مؤجلة إلى نطاق الأدلة الواردة.
- لا مسودة مالية منشورة: يمكن أن تكون المسودة محلية في النافذة، لكن الحفظ ينشئ مستنداً صحيحاً أو لا ينشئ شيئاً.
- لا إدخال مستند بتاريخ مستقبل، ولا تعديل صامت أو حذف بعد الحفظ.

## دورة العمل المعتمدة

```text
اختيار الشركة → إدخال فاتورة المورد أو مصروف
→ تحقق خادمي من المورد/الفئة/التاريخ/الضريبة/التكرار
→ اختيار: مدفوع من خزينة أو مستحق للمورد
→ Transaction واحدة: المستند + التسوية + Journal + Audit + idempotency receipt
→ سجل المستندات → فتح التفاصيل → تعديل في فترة مفتوحة أو إلغاء محاسبي بسبب
```

- **مدفوع:** مدين حساب الفئة (والضريبة القابلة للاسترداد إن انطبقت) ودائن حساب/حسابات الخزائن؛ مجموع التوزيعات يساوي إجمالي الفاتورة تماماً.
- **مستحق:** ينشئ التزام المورد من خلال مسار الاستحقاقات المعتمد؛ الدفع اللاحق يبقى عملية مستقلة ويخصم من الخزينة عند حدوثه.
- **تعديل داخل فترة مفتوحة:** يعيد الخادم بناء الأثر الجاري في transaction واحدة مع أثر قبل/بعد؛ بعد إقفال الفترة لا يتم إلا بمسار تصحيح/إلغاء معتمد.
- **الإلغاء:** يعكس الأثر ولا يحذف المصدر أو رقمه أو دليله.

## الصلاحيات

- `finance.purchase_expense.read` — عرض السجل والتفاصيل ضمن الشركة.
- `finance.purchase_expense.create` — إنشاء مستند.
- `finance.purchase_expense.correct` — تعديل مستند في فترة مفتوحة.
- `finance.purchase_expense.cancel` — إلغاء محاسبي بسبب إلزامي.
- `finance.supplier_dues.create` و`finance.supplier_dues.payment.record` تبقى منفصلة؛ لا تمنحها صلاحية العرض أو إنشاء المصروف وحدها.

لا يسمح النظام للمستخدم باختيار الشركة من جسم الطلب؛ CompanyContext والسياق الزمني والصلاحية تحسم خادمياً في كل عملية.

## بوابة Gate B

1. عقود Zod مشتركة للإنشاء والتعديل والإلغاء والقراءة وإيصالاتها.
2. نماذج ومهاجرة additive مع مفاتيح خارجية مركبة tenant/company وRLS/FORCE RLS.
3. أوامر idempotent وسجل Audit وJournal مختوم، بلا قيد يدوي من المتصفح.
4. اختبارات: عزل الشركات، منع الصلاحية، تطبيع رقم فاتورة المورد، تساوي التوزيع، لقطة الضريبة، replay، rollback ذري، تعديل الفترة المفتوحة وإلغاء الفترة المقفلة.
5. واجهة أصلية بعد إثبات الخادم: زر إضافة مستند، نافذة مضغوطة، سجل DataTable، تفاصيل برقم المستند، وفلاتر الفترة المركزية.

دفعات جماعية، طلبات شراء وموافقاتها، استلام مخزون، رفع ملف فعلي، OCR، بريد/Telegram، كشف بنك، ضريبة/إقرار، تقارير ومهارات بصيرة. تضاف كل قدرة بقرار نطاق مستقل بعد إغلاق هذه الشريحة.
