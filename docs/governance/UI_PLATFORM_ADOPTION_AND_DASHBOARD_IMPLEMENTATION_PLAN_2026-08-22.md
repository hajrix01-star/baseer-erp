# قرار وخطة التحول لمنصة الواجهة والمكتبات — 2026-08-22

**الإصدار:** 2.0 · **الحالة:** خطة تحول معتمدة فنياً بمراجعة خبراء؛ لا تفعّل نطاق تنفيذ ولا تغيّر أولوية التسليم وحدها · **المالك المطلوب:** مالك بصير لاختيار النطاق النشط قبل أي تغيير برمجي.
**المرجع الحاكم:** [سلطة التسليم الحالية](CURRENT_DELIVERY_AUTHORITY.md)، [بروتوكول التسليم](DELIVERY_CONTROL_PROTOCOL.md)، [ميثاق لجنة الجودة](ACCEPTANCE_AND_QUALITY_COMMITTEE_CHARTER.md)، [معيار واجهة بصير](BASEER_UI_SYSTEM_STANDARD.md)، و[معيار نظام المكونات](DESIGN_SYSTEM_AND_COMPONENT_STANDARD.md).

## 1. إعلان العمل المسموح الآن

```text
النطاق النشط: Baseer UI Platform Enablement — Phase 0 baseline وPilot واحد.
مرحلة التسليم: Design ثم Phase 0 baseline فقط حتى تحقق بوابته.
حدود التفويض: Combobox واحد غير مالي عبر React Aria؛ لا Dashboard أو ترحيل شامل.
دليل الانتقال: baseline نظيف، سجل تبعية، وخطة اختبار مقبولة من مراقبي الجودة والتسليم.
```

التفويض الحالي يسمح فقط بـPhase 0 وpilot واحد غير مالي؛ لا يسمح بإطلاق لوحة جديدة أو إعادة كتابة واجهات. لا يثبت اعتماد ولا يعدل `package.json` قبل نجاح baseline وتسجيل قرار التبعية في السجلات الحاكمة.

## 2. القرار التنفيذي

يعتمد بصير نهجاً هجيناً:

1. تبقى ملكية بصير كاملة للهوية العربية، RTL/LTR، اللغة، تدفقات ERP، الحسابات، القراءة الخادمية، العزل، والصلاحيات.
2. تعتمد المكتبات فقط للسلوك العام المتكرر الذي لا يمثل ميزة تنافسية: الإتاحة، إدارة التركيز، القوائم، النماذج، الجداول الكثيفة، والرسوم.
3. لا يدخل قالب لوحة تحكم أو نظام تصميم كامل أو إطار CSS عالمي. طبقة `Baseer*` هي العقد المرئي الوحيد الذي تستهلكه الشاشات.
4. لا تعيد الخطة كتابة ما يعمل. الترحيل يتم عند لمس تدفق محدد وبعد تكافؤ الاختبارات، ثم تزال البدائية القديمة في تغيير مستقل.

## 3. لماذا الآن

تظهر مراجعة اللجنة أن الواجهة الحالية تحتوي 10,803 أسطر TypeScript/TSX و3,931 سطر CSS موزعة على 23 ملف CSS. يوجد نظام داخلي صالح (`BaseerButton` والبطاقات والحوارات والجداول)، لكن سلوكيات عامة معقدة يجري صيانتها محلياً مثل الحوار، البحث والاختيار، الـportal، إدارة التركيز، والتقويم.

لقطة الحالة المحلية بتاريخ 2026-08-22:

- `npm run check --workspace @baseer-erp/web`: **Pass**.
- `npm run verify:web-budget`: **Fail** في شجرة العمل الحالية: CSS الابتدائي `58,688 B` مقابل حد `58,000 B`.
- هذه نتيجة تشخيصية لشجرة عمل غير نظيفة، وليست استبدالاً لأدلة الجودة المسجلة سابقاً؛ يجب إعادة بناء baseline قبل بدء أي Spike.

الهدف ليس زيادة عدد الاعتماديات، بل خفض كلفة الصيانة وتحسين الإتاحة دون كسر الميزانية أو الحقيقة الخادمية.

## 4. الأهداف وعدم الأهداف

### الأهداف

- تقليل بناء السلوكيات العامة يدوياً وتحسين لوحة المفاتيح وfocus وRTL.
- إبقاء كل تصميم بصري تحت CSS tokens ومكونات `Baseer*`.
- جعل النموذج الجديد والجداول الكثيفة والرسوم قابلة للبناء بسرعة وباختبارات أوضح.
- تقديم لوحة مالية دورية تقود إلى الإجراء، مع مصدر كل رقم وحالة جودة بياناته.
- المحافظة على قيود حجم الرحلة الفعلية، ومنع خروج بيانات مالية إلى SDK أو خدمة خارجية.

### ليست ضمن هذه الخطة

- إعادة تصميم التطبيق بالكامل أو استبدال الـShell.
- قالب Admin جاهز أو Tailwind/MUI/Ant Design كطبقة واجهة عامة.
- نقل التفويض من Nest/RLS إلى المتصفح أو إلى CASL.
- لوحة Widgets حرة الترتيب أو dashboard خارجي/SaaS.
- تغيير الحسابات المالية، عقود التقارير، Noorix، أو إطلاق إنتاج.

## 5. نموذج المعمارية المستهدف

```text
CSS tokens + اللغة والاتجاه المركزي
  -> Baseer primitives (BaseerDialog / BaseerCombobox / BaseerForm / BaseerDataGrid / BaseerChart)
    -> مكتبات Headless أو renderers انتقائية
      -> Shared patterns (FilterBar / ReceiptPanel / DashboardCard)
        -> شاشات الموديولات

Nest authorization + RLS + server read models
  -> عقود قراءة مصرح بها، كاملة وموسومة بجودة البيانات
    -> مكونات العرض فقط؛ لا حساب مالي أو قرار تفويض في المتصفح
```

تستهلك الشاشات مكونات `Baseer*` فقط. لا تستورد الشاشة `react-aria-components` أو ECharts أو TanStack مباشرة إلا باستثناء مكتوب ومقبول.

## 7. مراحل التنفيذ

كل مرحلة تتطلب نطاقاً نشطاً وتسجيل بدء العمل وفق بروتوكول التسليم. لا تبدأ المرحلة التالية قبل تحقق معيار قبول المرحلة السابقة.

### المرحلة 0 — Baseline والحوكمة

**الهدف:** جعل إدخال أول تبعية قابلاً للقياس والرجوع عنه.

**العمل:**

1. إعادة بناء الإنتاج من الشجرة المعتمدة، ثم تشغيل `check`, `build`, `verify:web-budget`, فحوص الحوار والحدود المالية والـlocalization ذات الصلة.
2. إزالة أو تقسيم CSS مكرر حتى يعود budget إلى النجاح؛ لا ترفع الحد العالمي.
3. إنشاء سجل قرار تبعية لكل مكتبة: السبب، المالك، النسخة المقفلة، الترخيص، حجم الرحلة، التبعيات العابرة، بديل الإزالة، وتاريخ المراجعة.
4. اعتماد `npm` و`package-lock.json` كمصدر lockfile وحيد ما دام CI يستخدم `npm ci`؛ يوثق قرار إزالة أو استبدال أي lockfile ثانٍ قبل إدخال تبعية.
5. اعتماد Rubric موحد: AR/EN، RTL/LTR، keyboard، focus، screen reader، mobile، `prefers-reduced-motion`، CSP، XSS، وقياس bundle.
6. تحديد مسار Pilot واحد لا يحمل بيانات مالية حساسة للبدائية الأولى.

**دليل القبول:** budget ناجح، baseline محفوظ، قرار مكتوب للـpilot، وعدم وجود تغيير لسلوك صلاحيات أو حقيقة مالية.

### المرحلة 1 — Pilot: Combobox قابل للوصول

**الهدف:** إثبات أن React Aria يخفض كلفة `BaseerSearchSelect` ومخاطر keyboard/focus من دون تغيير تجربة بصير.

**العمل:**

1. إضافة `react-aria-components` فقط؛ لا يضاف React Spectrum أو CSS framework أو مكتبة Headless ثانية في هذا الـpilot.
2. بناء `BaseerCombobox` واحد يحافظ على عقد بصير: `value` معرف نصي، و`remoteSearch(query, signal)` مؤجل وقابل للإلغاء، وlabel/description وtokens الخاصة ببصير.
3. نقل مثيل واحد غير مالي (اختيار مورد أو مادة مثلاً)؛ لا توجد هجرة جماعية ولا تغيير لعقد API.
4. حماية البحث البعيد بـdebounce و`AbortController` وحماية سباق النتائج، وربط كل طلب بسياق الشركة والجلسة.
5. توثيق API للمكوّن: الحالات، ARIA، keyboard، RTL، mobile، tokens، وقيود `className`.
6. إضافة اختبارات Playwright: Tab/Shift+Tab، الأسهم، Home/End، Enter، Escape مع عودة focus، mouse/touch، AR/EN، RTL/LTR، شاشة ضيقة، وفتحه داخل `BaseerDialog`.

**دليل القبول:** تكافؤ تدفق المستخدم، local/remote search وloading/empty/error، عدم تسرب نتائج بين الشركات، تحسن قابل للقياس في الكود أو الاختبار، نجاح budget، وعدم وجود portal/focus/RTL regression.

### المرحلة 2 — النماذج والجداول بحسب الحاجة المثبتة

**الهدف:** نقل أعلى نقاط التكرار، لا كل الواجهة.

**العمل للنماذج:** إنشاء adapters مركزية للحقول ورسائل الخطأ مع React Hook Form + `@hookform/resolvers` + Zod 4؛ تطبيقها أولاً على نموذج مستخدم أو موظف غير مالي. تبقى عقود API والخادم أصحاب التحقق النهائي. لا تستخدم `z.coerce.number()` أو أرقام JavaScript للأموال؛ تبقى Decimal strings وتتحقق خادمياً.

**العمل للجداول:** قبل TanStack، يثبت API pagination/filter/sort خادمياً. ثم يبنى `BaseerDataGrid` لسجل واحد كبير، مع حالة loading/error/empty، مفاتيح ثابتة، استراتيجية جوال، وفرز كـintent يرسله إلى الخادم.

**العمل لحالة القراءة:** بعد توثيق سياسة cache، يجرّب `@tanstack/react-query` في مساحة قراءة واحدة فقط. يتضمن مفتاح الاستعلام `tenant/company/principal/capability-version/locale/filters` عند انطباقها، ويمسح الـcache عند sign-out أو تبديل الشركة أو تغير الصلاحية. لا تستخدمه كسلطة حسابية أو cache دائم لنتائج مالية.

**دليل القبول:** رسائل عربية/إنجليزية، focus لأول خطأ، لا رسائل خادم خام، لا يوجد حساب مالي في المتصفح، اختبارات denied role وcompany isolation تمر، ولا يزيد حجم الرحلة فوق الحد.

### المرحلة 3 — لوحة مؤشرات مالية تجريبية

**الهدف:** لوحة واحدة لدور واحد، تسرّع القرار ولا تستبدل السجل أو التقرير.

**التصميم الوظيفي للنسخة الأولى:**

1. المستخدم المستهدف: مالك الشركة أو مدير مالي يملك صلاحية قراءة صريحة.
2. سياق ثابت أعلى الصفحة: الشركة، الفترة، وقت إنشاء القراءة، وحالة جودة البيانات.
3. أربع بطاقات فقط: صافي المبيعات المثبتة، الداخل/الخارج الفعلي، الرصيد النقدي as-of، وعناصر تحتاج إجراء.
4. قائمة «يحتاج إجراء» أهم من الرسم؛ كل عنصر يفتح السجل أو الإجراء المصرح به.
5. رسم واحد فقط لخط اتجاه 30 يوماً أو فترة مماثلة. لا يدعي سببية ولا يملأ الأيام المفقودة بصفر.
6. رسم وحركة هادئان: 150–250ms عند التحميل/تبديل الفترة، مع `prefers-reduced-motion`. لا عدّاد متحرك للأرصدة المدققة.

**عقد القراءة المطلوب قبل الواجهة:** endpoint أو read model خادمي محدد يعيد `companyId`, `period`, `asOf`, `generatedAt`, `metricCode`, `definitionVersion`, `sourceCoverage`, `dataQuality`, `basis`, `currency`, `timezone`, `metrics`, `actionItems`, `series`، ومراجع drill-down. الخادم يجمع ويصرح ويصف البيانات؛ الواجهة تعرضها فقط. كل مبلغ يحمل أساسه ولا يحسب من صفوف محمّلة جزئياً.

**قواعد ECharts:** import للـcharts/components/renderers المطلوبة فقط، بما فيها `AriaComponent` صراحة؛ lazy import داخل workspace؛ `aria.show: true` ووصف عربي/إنجليزي؛ ملخص HTML مرئي وجدول بيانات قابل للوصول يطابق الرسم؛ `ResizeObserver` و`dispose` عند unmount؛ لا HTML formatter أو روابط غير موثوقة في tooltip؛ ألوان مع نص/شارة أو decal لا اللون وحده.

**دليل القبول:** API/RBAC/RLS ومالية القراءة موثقة، AR/EN + RTL/LTR وmobile، accessibility، budget، ومراجعة BAQC-02/03/04/05/06/08/09/10 وقبول مالك للدور المحدد.

### المرحلة 4 — الصلاحيات والتوسّع المتحكم به

**الهدف:** منع اختلاف واجهة library عن السياسة الحية.

**العمل:**

1. توحيد حارس خادمي أو decorator لتفويض الشركة بدلاً من تكرار أنماط authorize في controllers الجديدة.
2. مراجعة سياسة منح مدير الشركة تلقائياً كل صلاحيات القالب؛ أي صلاحية مالية حساسة جديدة تتطلب opt-in/ترقية صريحة ومراجعة أثر الأدوار القائمة.
3. إضافة اختبارات سلبية لكل مسار جديد: مستخدم بلا صلاحية، شركة أخرى، مستأجر آخر، جلسة مسحوبة، وصلاحية أزيلت أثناء الجلسة.
4. يحتفظ `<Can>` الداخلي بوظيفة الإخفاء/التعطيل التفسيرية فقط. لا يدخل CASL إلا بعد وجود سياسة خادمية حقيقية حسب السجل أو الفرع أو حالة المستند وقرار مراجعة جديد.
5. إضافة الأمن الأساسي قبل التوسعة: Helmet، CSP report-only ثم enforce، CORS allowlist عند وجود origin منفصل، وtrust proxy بقائمة موثوقة لا قيمة عامة. لا يفعّل HSTS إلا بعد إثبات TLS عند الـedge.
6. تطبيق حصص Throttler مسماة للمصادقة والاسترداد وAI. التخزين in-memory مسموح فقط مع توثيق API replica واحدة؛ قبل replica ثانية يلزم مخزن ذري مشترك واختبار cross-replica.

**دليل القبول:** مصدر تفويض واحد في الخادم، لا كشف بطاقة/إجراء حساس في الواجهة، ودليل denied-path قابل لإعادة التشغيل.

### المرحلة 5 — الترحيل عند اللمس والتنظيف

**الهدف:** خفض الدين الفني من دون مخاطرة هجرة واسعة.

**العمل:** عند تعديل شاشة لاحقة، تستبدل البدائية الموروثة بالمكوّن المركزي المعتمد فقط إذا حققت التكافؤ. بعد نقل كل المستهلكين واختبارهم، تزال البدائية السابقة وCSS الخاص بها في تغيير مستقل.

**دليل القبول:** لا توجد نسختان تعملان للسلوك نفسه، ولا CSS مكرر، وكل حذف محمي باختبارات regression وbudget.

## 9. المخاطر والضوابط

| الخطر | الضبط |

| تضخم JS/CSS أو فشل budget | headless/modular imports، lazy routes، قياس بعد كل Spike، لا CSS framework عالمي |

| توسيع صلاحيات صامت لمدير الشركة | سياسة opt-in للصلاحيات الحساسة ومراجعة migration/roles قبل الإصدار |

## 11. قرار المالك المطلوب قبل البناء

يعتمد المالك بالترتيب التالي:

1. تفويض نطاق عابر محدود باسم **«تمكين منصة واجهة بصير — المرحلة 0 وPilot React Aria واحد»**، أو تأجيله حتى اختيار نطاق أعمال جديد.
2. اعتماد `BaseerCombobox` عبر React Aria كـpilot أول، في مسار غير مالي؛ أي تحويل لبدائية أخرى يمر بـADR بعد أدلة المرحلة 1.
3. اعتماد الأمن الأساسي وشرط replica=1 قبل توسيع مسارات الهوية أو AI؛ ولا يعد التخزين in-memory حماية موزعة.
4. تأكيد أن لوحة المالية التجريبية تأتي بعد نجاح الـpilot، وليست استبدالاً للتقارير أو قبولاً لإصدار إنتاج.
5. قبول قرار تأجيل CASL حالياً، ومراجعة منح صلاحيات مدير الشركة الحساسة في المرحلة 4.

## 12. تعريف نجاح الخطة

تعد الخطة ناجحة عندما يثبت أول Pilot أن بصير يقدم سلوكاً أفضل أو كوداً أقل مع بقاء الهوية العربية، مع مرور budget والاختبارات؛ ثم تبنى لوحة مالية واحدة من قراءة خادمية موثقة تعطي المستخدم إجراءً واضحاً. لا يقاس النجاح بعدد المكتبات المثبتة أو عدد الشاشات التي أعيدت كتابتها.

## 13. خط الأمن الأساسي

تطبق الضوابط التالية كجزء من التمكين، لا كوعود عامة:

1. لا تسجل logs أو traces كلمات المرور أو tokens أو bodies أو PII؛ تبقى الاستجابة المصرح بها `no-store, private`.
2. يختبر Helmet وsecurity headers في كل بيئة. يبدأ CSP بوضع report-only، ثم يتحول إلى enforce بعد اختبار SPA وملفات الرفع؛ لا يفترض CORS إن كان التطبيق والـAPI على origin واحد.
3. تستخدم المصادقة الحالية bearer token؛ قواعد Secure/HttpOnly/SameSite/CSRF تصبح إلزامية فقط إذا تقرر نقلها إلى cookies. لا يؤجل ذلك حماية XSS وCSP الحالية.
4. تملك نقاط sign-in وrefresh وreset وowner activation وAI حصصاً مستقلة أشد من القراءة العامة، بمفتاح IP ومعرّف تسجيل دخول مطبّع أو user/company حيث يتاح. لا يسمح `skipOnError` لهذه النقاط، ولا يكشف الرد وجود الحساب.
5. قبل أكثر من API replica واحدة، يعتمد مخزن rate limit ذري مشترك وتختبر مفاتيحه وTTL وproxy وIPv4/IPv6 والمرور عبر النسخ؛ تفشل مسارات الهوية وAI بصورة آمنة عند تعطل هذا المخزن.

## 14. أدوات مؤجلة وفق محفزات قابلة للقياس

| الأداة | متى تدرس | الحد المعماري |
| --- | --- | --- |
| PostgreSQL FTS + `pg_trgm` | عند وجود فجوة بحث مثبتة في ثلاثة مجالات | فهارس/وثائق محدودة مع RLS؛ لا فهرسة تلقائية للقيود أو الرواتب أو المرفقات الحساسة |
| `pg-boss` | تصدير ثقيل أو إعادة فهرسة أو retry مجدول | envelope يحمل tenant/company/actor/correlation/idempotency/entity-version؛ worker يفتح tenant transaction؛ الأثر المالي في المعاملة الأصلية فقط |
| TanStack Virtual | قياس موثق لمشكلة DOM في سجل كثيف | لا يستخدم لمجرد توقع الأداء؛ يبقى الفرز والتصفية خادميين |
| OpenTelemetry | حاجة تشغيلية مثبتة بعد تصنيف البيانات | لا مصدر خارجي قبل retention/encryption/egress allowlist؛ لا PII في traces |
| Cube أو طبقة تحليلات مستقلة | ثلاثة مستهلكين تحليليين مستقلين أو حمل واضح | read replica/projections فقط؛ لا اتصال كتابي بقاعدة المال ولا تجاوز RLS |
| CASL | قواعد خادمية مثبتة حسب سجل/فرع/حالة | spike خادمي versioned يقارن النتائج مع policy/RLS؛ لا سلطة عميل مستقلة |

## 15. حوكمة التبعيات والإصدارات

1. لكل تبعية مالك وADR أو سجل سبب، ترخيص، peer dependencies، حجم، تاريخ مراجعة، وخطة إزالة.
2. تثبت نسخ React Hook Form وresolvers وZod بدقة بعد فحص peer dependencies؛ تستخدم المنصة Zod 4 واحدة مشتركة مع العقود، ولا تثبت RHF/resolvers في حزمة العقود.
3. تبقى `package-lock.json` حتمية مع `npm ci`. لا تقبل تغييرات اعتماد بلا lockfile محدث؛ قرار `pnpm-lock.yaml` يكون إزالة صريحة أو انتقال CI كامل، لا حالتين معاً.
4. يطبق CI: `npm ci` وtypecheck/build/tests وaudit إنتاجي وlockfile integrity وDependency Review/Dependabot. لا تدمج ترقية أمنية تمس auth أو Prisma أو Fastify تلقائياً بلا smoke/security tests.
5. **قرار 2026-08-22:** `npm` و`package-lock.json` هما المصدر المعتمد الوحيد؛ لا يستخدم `pnpm-lock.yaml` في CI أو التثبيت ويزال من الشجرة المحلية قبل أول اعتماد جديد.
