# BASEER ERP — التفويض التشغيلي لاعتماد المكتبات

**المالك:** مالك BASEER ERP
**ساري من:** 2026-08-22
**الغاية:** تمكين اعتماد مكتبات جديدة لاحقاً دون طلب تفويض مالك منفصل لكل مكتبة، مع إبقاء بوابات الأمان والجودة والعزل إلزامية.

## التفويض

يفوّض هذا القرار فريق BASEER باكتشاف، وتجربة، ودمج مكتبة واحدة في كل
مرحلة مستقلة متى استوفت بوابات هذا المستند. لا يلزم تفويض جديد للمكتبة
نفسها أو للمكتبة التالية إذا بقيت ضمن الفئات والحدود أدناه.

يشمل التفويض المكتبات التي تحل سلوكاً عاماً لا منطق أعمال خاصاً، مثل:

- مكوّنات واجهة headless وإتاحة وتقويم وحوار وقوائم.
- النماذج والتحقق على الواجهة، والجلب/cache للقراءة، والجداول الكبيرة.
- الرسوم البيانية والتصور المحلي للبيانات الخادمية.
- الاختبارات، الإتاحة، قياس الأداء، والتحقق من التبعيات.
- رؤوس حماية API وتحديد معدل الطلبات لنقاط حساسة، من دون تغيير نموذج
  المصادقة أو سياسة التفويض أو بنية النشر.

قاعدة الدمج دائماً: `Library → Baseer adapter → application`. لا تستورد
الشاشات المكتبة مباشرة، ولا تدخل CSS framework أو theme عالمياً.

## ما يبقى خارج التفويض التلقائي

يتطلب قرار مالك صريحاً ومكتوباً قبل البدء، ولا يغطيه هذا المستند:

- مكتبة تفويض أو تغيّر RBAC/RLS/CompanyContext أو قرار وصول للسجل.
- مكتبة تمس قيوداً مالية، حسابات مبالغ، تواريخ أعمال، أو مصدر الحقيقة.
- قاعدة بيانات، migration engine، queue/broker، cache موزع، أو محرك بحث.
- SaaS أو telemetry أو CDN أو أي إرسال بيانات مالية/HR إلى طرف خارجي.
- قالب إدارة كامل، CSS framework عالمي، أو تغيير React/Vite/Nest/Prisma/Node.
- نشر إنتاجي، تغيير بنية الاستضافة، أو قبول الاستثناءات الأمنية عالية الخطورة.

## بوابة كل مكتبة

يفتح المنفذ سجل اعتماد قبل التثبيت يتضمن: المشكلة الفعلية، المالك،
الإصدار الدقيق، الترخيص، peer/transitive dependencies، الحجم المتوقع،
خطة الإزالة، وأول مستهلك معزول. ثم لا تُدمج المكتبة إلا عند اكتمال:

1. `npm ci` وlockfile واحد، مراجعة الرخص والتبعيات، وفحص اعتماد التشغيل.
2. TypeScript/build/bundle budget، من دون رفع الحد لتمرير مكتبة.
3. AR/EN وRTL/LTR، keyboard/focus، mobile، reduced motion وaxe/Playwright.
4. Baseer adapter واختبار عقده؛ لا استيراد مباشر من الشاشة.
5. عزل الشركة والجلسة، وإلغاء الطلبات القديمة، وعدم حفظ بيانات شركة أخرى.
6. لا منطق مالي أو قرار صلاحية في المتصفح؛ الـAPI وRLS هما السلطة.
7. PR/commit صغير مع دليل قابل لإعادة التشغيل، ثم قرار مراقب الجودة:
   Pass أو Return أو Blocked.

الفشل أو advisory حرج/عالٍ جديد، تجاوز budget، تسرب بيانات، أو فشل عزل
شركة يوقف تلك المكتبة فقط. لا يوقف المكتبات الأخرى ما لم يكن السبب مشتركاً.

## التسلسل الافتراضي

الترتيب المصرح به، مع الانتقال تلقائياً بعد اجتياز بوابة المرحلة السابقة:

1. React Aria: Date/Dialog بعد Combobox.
2. React Hook Form + `@hookform/resolvers` + Zod: نموذج غير مالي.
3. TanStack Query: تدفق قراءة مع company-aware cache.
4. ECharts: لوحة واحدة من read model خادمي مع جدول/ملخص قابل للوصول.
5. TanStack Table أو Virtual: فقط عند قياس جدول كبير يثبت الحاجة.

لا يفرض هذا الترتيب تثبيت كل مكتبة؛ يمكن تجاوز مكتبة لا تظهر لها مشكلة
حقيقية، ويُسجل السبب في سجل الاعتماد.
