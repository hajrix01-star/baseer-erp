# تدقيق الأقسام والتبويبات والصلاحيات — BASEER ERP

الحالة: تقرير تدقيق قبل تنفيذ فصل التبويبات — 24 أغسطس 2026.

## النتيجة التنفيذية

**يمكن منح وسحب الصلاحيات من الأدوار حالياً**؛ كتالوج الصلاحيات ثابت ومدار من واجهة الأدوار، والخادم يفوض كل طلب ضمن الشركة. لكن لا يمكن القول إن كل تبويب قابل للعزل الآن: توجد شاشات تجمع عدة تبويبات تحت صلاحية واحدة، وبعضها يحمل البيانات المشتركة قبل تحديد التبويب.

لا يكفي إخفاء زر أو تبويب. القبول الصحيح لأي صلاحية هو: لا يظهر التبويب، ولا تُحمّل بياناته، ولا يقبل الخادم رابطه أو طلبه من مستخدم لا يملكها.

## ما تمت مراجعته

- كل الأقسام الظاهرة في [modules.ts](../../apps/web/src/modules.ts): مركز القيادة (4)، القرار (5)، التسويق (5)، البريد والأدلة (3)، العمليات (10)، المالية (5)، الموارد البشرية (7)، التقارير (5)، والإدارة (6).
- قواعد إظهار الأقسام في [module-access.ts](../../apps/web/src/module-access.ts).
- جميع التبويبات المباشرة في الويب، والمسارات وقيود الصلاحية المقابلة في Controllers الخادم.
- كتالوج الصلاحيات والأدوار القابلة للتعديل في `apps/api/src/administration/administration-permissions.ts` وواجهة الأدوار.

## فجوات مؤكدة يجب علاجها

1. **قاعدة السماح الافتراضي في التنقل.** `module-access.ts` يعيد السماح إذا لم توجد قاعدة للقسم. يجب استبداله بقاعدة منع افتراضي بعد تحميل الصلاحيات، مع تعريف صريح حتى للأقسام العامة.
2. **المشتريات.** المستخدم ذو `finance.purchase_expense.create` يرى تبويبات السجل والآجل حالياً، كما أن تحميل الصفحة يطلب بيانات سجل قد يرفضها الخادم. هذا أول سطح يجب إصلاحه.
3. **المصروفات والالتزامات.** القراءة الخادمية مجمعة في خدمة واحدة تطلب ثلاث صلاحيات؛ لا يمكن تقديم دور محدود صحيح قبل تقسيمها.
4. **الموظف ونهاية الخدمة.** التبويبات والأزرار تحتاج مصفوفة وصول صريحة، رغم أن API يملك كثيراً من صلاحيات الأفعال اللازمة.
5. **التقارير والإدارة.** لا تظهر أقسام بلا قاعدة صريحة؛ يجب إما ربطها برمز أو إزالتها من التنقل إلى أن تتوفر لها خدمة مكتملة.

## النموذج الاحترافي المقترح

لكل قسم أو تبويب أو إجراء قابل للتفويض نعرّف سجلاً واحداً:

```ts
type PermissionSurface = {
  id: string;                         // مثال: operations.purchases.history
  kind: "page" | "tab" | "action";
  requiredAny?: readonly PermissionCode[];
  requiredAll?: readonly PermissionCode[];
  apiResources: readonly string[];    // endpoints التي يجب أن تعطي النتيجة نفسها
  fallback: "hide" | "safe-default";
};
```

يرسم الويب فقط الأسطح المسموح بها، ويستدعي بياناتها عند فتحها فقط. تتطابق صلاحية كل endpoint مع السطح الذي يخدمه؛ لا يعيد endpoint واحد بيانات ثلاثة تبويبات مختلفة. يبقى تفويض API وRLS المصدر الأمني النهائي.

## ترتيب التنفيذ المقترح

1. منع السماح الافتراضي وإضافة قواعد صريحة للأقسام غير المعرفة.
2. فصل المشتريات إلى: مراجع إدخال محدودة، سجل، وآجل؛ ثم اختبار دور «مدخل مشتريات» بلا سجل وبلا آجل.
3. فصل قراءة المصروفات والالتزامات إلى endpoints حسب التبويب.
4. إضافة مصفوفة تبويبات لملف الموظف والسلف ونهاية الخدمة، مع إخفاء الأفعال غير المصرح بها.
5. تقرير قرار تجاري للتقارير: هل `reports.read` يكفي أم نحتاج رموزاً مستقلة لكل تقرير مالي/ضريبي؟
6. إضافة اختبارات E2E لكل دور محدود: عدم ظهور السطح، فشل الرابط المباشر، ورفض API.

## بوابة القبول

مثال «مدخل مشتريات» لا يمنح إلا `finance.purchase_expense.create` مع مراجع الإدخال المحدودة المعتمدة. يجب أن يرى تبويب الإدخال وحده، وألا تظهر أو تُحمّل بيانات السجل أو الآجل، وأن تعود محاولة فتحها المباشرة إلى وجهة آمنة مع رفض خادمي موثق.

## التنفيذ الموسّع — 24 أغسطس 2026

- **المصروفات والالتزامات:** فُصلت القراءة الخادمية إلى ثلاثة endpoints مستقلة:
  - `GET /finance/expenses-obligations-workspace/items` — يتطلب إعدادات المالية + القروض + قراءة المشتريات.
  - `GET /finance/expenses-obligations-workspace/batch` — يتطلب إعدادات المالية + قراءة المشتريات فقط.

- **الأفعال الدقيقة:** حُجبت واجهات تعديل الموظف، تسجيل الترقية، إدارة الراتب، إنشاء/استبدال/إلغاء/تنزيل مستند، إصدار/إلغاء خطاب، وعمليات نهاية الخدمة وفق رموزها الخادمية المقابلة.
