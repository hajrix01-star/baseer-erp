# BASEER ERP — سياسة قبول خطر Prisma للنشر الشخصي الخاص

**الحالة:** معتمدة بقرار المالك في 2026-08-22

**النطاق:** تطوير BASEER بالكامل، ودمج المصدر، والتحقق، والنشر الخاص المملوك
لصاحب النظام

**المرجع الأمني:** `GHSA-ggr8-5vv4-36mx` / `CVE-2026-40345`

## القرار

يقبل مالك BASEER مؤقتاً الخطر السياقي الناتج عن
`prisma@7.9.1 → @prisma/config@7.9.1 → deepmerge-ts@7.1.5` داخل **أدوات
البناء والمهاجرات فقط**. لا تمنع هذه النتيجة إكمال أقسام المشروع أو دمج
المكتبات المؤهلة أو نشر BASEER أونلاين بصورة شخصية وخاصة، ما دامت الضوابط
الإلزامية في هذه السياسة مستمرة.

هذا قبول خطر وليس إصلاحاً للمكتبة. يبقى التصنيف العام للنشرة High، بينما
التعرض السياقي في BASEER منخفض: الاستغلال يحتاج كائنات JavaScript دورية،
ولا تنشئها طلبات JSON العادية؛ وإعداد Prisma محلي وثابت ولا يأخذ مدخلات من
المستخدم. الأثر المتوقع إن تحقق هو تعطل عملية CLI أو migration، وليس كشف
بيانات أو تعديلها أو تجاوز RLS.

نتائج `npm audit` الثلاث (`prisma` و`@prisma/config` و`deepmerge-ts`) تمثل
مساراً واحداً لنفس النشرة، وليست ثلاث ثغرات مستقلة.

## ما تسمح به السياسة

- إكمال جميع أقسام BASEER وفق بوابات كل قسم المعتادة.
- دمج المكتبات المؤهلة خلف Baseer adapters وفق تفويض اعتماد المكتبات.
- التطوير والاختبار والبناء ودمج المصدر.
- النشر الأونلاين الشخصي الخاص باستخدام صور Docker المعتمدة.
- تشغيل `prisma migrate deploy` كمهمة داخلية قصيرة العمر عند أول نشر أو عند
  وجود migrations جديدة.

لا تمنح هذه السياسة قبولاً تلقائياً لوظائف غير مكتملة، ولا تتجاوز اختبارات
المال أو العزل أو الصلاحيات أو النسخ الاحتياطي، ولا تعتبر المشروع SaaS-ready.

## الضوابط الإلزامية

1. تستخدم API صورة `runtime` من `Dockerfile` فقط. يجب أن يفشل بناؤها إن وجد
   فيها `prisma` أو `@prisma/config` أو `deepmerge-ts`.
2. لا تشغّل Prisma CLI أو migrations عند بدء API أو أثناء خدمة طلبات
   المستخدمين.
3. تبقى مهمة `migrate` بلا منفذ عام، على شبكة قاعدة البيانات الداخلية،
   قصيرة العمر، بنظام ملفات read-only و`no-new-privileges`.
4. يبقى `apps/api/prisma.config.ts` وملفات migrations من المصدر الموثوق
   المقفول بـ`package-lock.json`، ولا يسمح بإعداد خارجي أو remote extend أو
   محتوى يولده مستخدم.
5. يبقى التسجيل العام مغلقاً، ويقتصر النشر على المالك والمستخدمين الذين
   يصرح لهم. أي انتقال إلى SaaS أو بيع تجاري أو تسجيل عام يلغي هذا القبول
   ويعيد النشرة إلى بوابة إصدار مانعة.
6. لا يستخدم `npm audit fix --force`، ولا downgrade إلى Prisma 6، ولا Prisma
   RC/Next، ولا override لـ`deepmerge-ts` دون نطاق توافق مستقل وقرار مالك.
7. أي ثغرة High/Critical تصل إلى صورة API التشغيلية ليست مشمولة بهذا
   الاستثناء وتوقف الإصدار.

## إجراء كل نشر

1. أخذ نسخة احتياطية قابلة للاستعادة من PostgreSQL قبل أي migration.
2. البناء من `package-lock.json` باستخدام `npm ci` وبناء صورتي `runtime`
   و`migrate` من نفس revision.
3. إثبات أن graph التشغيل المنشور نظيف عبر
   `npm audit --omit=dev --omit=optional`، وأن boundary الصورة يمنع حزم Prisma
   الثلاث من runtime.
4. تشغيل `npm run check:prisma-advisory-status` وتسجيل النتيجة. استمرار
   `pending-official-fix` مسموح بهذه السياسة فقط ما دامت بقية الضوابط تمر.
5. بعد جاهزية قاعدة البيانات، تشغيل مهمة `migrate` مرة واحدة. إذا لم توجد
   migrations جديدة تكون العملية no-op. فشلها يمنع rollout ولا يشغّل API
   الجديدة.
6. بعد نجاحها، التحقق من migration status وRLS/FORCE RLS والدور المقيد، ثم
   تشغيل readiness/health قبل تحويل الاستخدام إلى الإصدار الجديد.
7. الاحتفاظ بالإصدار السابق ونقطة الاستعادة حتى ينجح التحقق التشغيلي.

## المراجعة والإلغاء

- يفحص monitor قبل كل إصدار ومرة كل شهر أثناء استمرار النشرة.
- يراجع المالك قبول الخطر شهرياً؛ عدم وجود patch رسمي لا يوقف تطوير المشروع
  ما دامت الضوابط مستمرة.
- يلغى القبول فوراً إذا تسربت الحزمة إلى runtime، أو أصبحت Prisma config
  قابلة لمدخل خارجي، أو تعرضت مهمة migrate للشبكة العامة، أو تحول المنتج إلى
  SaaS/بيع/تسجيل عام، أو ظهرت ثغرة جديدة تغير أثر السرية أو سلامة البيانات.
- الإغلاق الدائم هو إصدار Prisma مستقر يعتمد `deepmerge-ts >=8.0.0`، ثم ترقية
  `prisma` و`@prisma/client` و`@prisma/adapter-pg` كحزمة متطابقة، وإعادة
  generate/validate/migrate وDB/RLS/HTTP/Docker/audit gates.

## النتيجة الحاكمة

هذه النشرة وحدها لم تعد مانعاً لإكمال BASEER أو لنشره الشخصي الخاص. تبقى
بوابات الجاهزية الأخرى مستقلة، ولا يجوز وصف النشرة بأنها «مغلقة» حتى يصل
الإصلاح الرسمي وتنجح إعادة التحقق.
