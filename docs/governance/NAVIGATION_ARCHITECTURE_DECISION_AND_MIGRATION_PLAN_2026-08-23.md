# قرار معمارية التنقل وترحيلها — BASEER ERP

الحالة: مسودة قرار معماري موصى بها للتنفيذ المرحلي — 23 أغسطس 2026.

## القرار التنفيذي

يعتمد النظام **سجل صفحات مركزي Typed Page Registry** تكون فيه هوية الصفحة ثابتة ومستقلة تماماً عن موضعها في القائمة.

مثال: صفحة إعدادات المالية تحمل المعرف الدائم `finance-settings`، سواء ظهرت أولاً أو أخيراً في الشريط الجانبي. ترتيبها المرئي خاصية مستقلة مثل `navigation.order` ولا يغيّر الرابط أو الصلاحيات أو الأيقونة أو المحتوى.

المسار القانوني الجديد في مرحلة الانتقال هو:

```text
#module=finance&page=finance-settings
```

ويبقى المسار القديم، مثل `#module=finance&section=0`، قابلاً للقراءة فقط عبر طبقة توافق ثم يحوَّل بهدوء إلى المسار القانوني. لا يضاف أي رابط أو قسم جديد بالصيغة الرقمية.

## لماذا يلزم هذا القرار

حالياً رقم `section` هو الهوية الفعلية للصفحة. الدليل موجود في عدة طبقات:

- [modules.ts](../../apps/web/src/modules.ts) يخزن العناوين العربية والإنجليزية كمصفوفات متوازية، وبالتالي الموضع هو الهوية.
- [App.tsx](../../apps/web/src/App.tsx) يقرأ ويكتب `#module=…&section=N`، ويخزن هذا الرقم في الجلسة و«الأخيرة»، ويختار العنوان والمحتوى وفقه.
- [module-access.ts](../../apps/web/src/module-access.ts) يربط صلاحيات الاستكشاف بـ`module + section`.
- [baseer-section-icon.tsx](../../apps/web/src/baseer-section-icon.tsx) يربط الأيقونة بالموضع في مصفوفة.
- خدمة تقرير الأداء النقدي والعقد المشترك يصدران ويتحققان من روابط رقمية؛ كما توجد روابط داخلية واختبارات E2E بهذه الصيغة.

لذلك نقل «إعدادات المالية» اليوم قد يغيّر، من دون خطأ ظاهر، وجهة رابط محفوظ أو صلاحية أو محتوى أو أيقونة. هذا خلل معماري وليس مسألة تصميم القائمة.

## النموذج المستهدف

كل صفحة قابلة للفتح تعرف مرة واحدة في سجل مركزي. الصلاحية النهائية تبقى دائماً للخادم؛ السجل يحدد فقط ما يظهر في واجهة المستخدم.

```ts
type PageId =
  | 'finance-settings'
  | 'finance-ledger'
  | 'treasury-banks'
  | 'finance-accounts'
  | 'finance-categories';

type PageDefinition = {
  id: PageId;                         // ثابت ولا يعاد استخدامه
  moduleId: ModuleId;
  title: { ar: string; en: string };
  icon: Glyph;
  navigation: { order: number; visible: boolean };
  requiredAnyPermissions?: readonly PermissionCode[];
  load: () => Promise<{ default: React.ComponentType }>;
  allowedState?: RouteStateSchema;
  legacySections?: readonly number[]; // مؤقتاً للروابط القديمة فقط
};
```

تُشتق من السجل نفسه جميع العناصر التالية: القائمة، العنوان، الأيقونة، اللون، أول صفحة مسموحة، شاشة المحتوى، العناصر الأخيرة، وقواعد إظهار الصفحة. لا يجوز أن تحتفظ هذه الطبقات بمصفوفات مواضع مستقلة.

تظل `stage` حالة عرض فرعية ومحددة لكل صفحة (مثل تبويب السجل أو التقرير)، وليست بديلاً عن هوية صفحة مستقلة. أي قيمة حالة غير معتمدة تُرفض أو تعود إلى الحالة الآمنة الافتراضية.

## البدائل التي درستها اللجنة

| البديل | الحكم | السبب |
| --- | --- | --- |
| إعادة ترتيب مصفوفة الأقسام فقط | مرفوض | يبدّل المعنى الصامت للروابط والصلاحيات والمحتوى.
| إبقاء الرقم وإضافة خريطة رقمية له | مرفوض كحل دائم | يخفي التعقيد ولا يفصل الهوية عن العرض.
| سجل صفحات بمعرفات ثابتة فوق نظام الـHash الحالي | **موصى به الآن** | احترافي، تدريجي، ويحافظ على بيئة النشر الحالية والروابط القديمة.
| السجل نفسه مع React Router ومسارات مثل `/finance/settings` | خيار مستقبلي جيد | يحسن دلالة URL والتحميل المتداخل، لكنه لا يحل المشكلة وحده ويتطلب مراجعة الاستضافة والمصادقة والتاريخ.
| قوائم من قاعدة البيانات لكل شركة | مؤجل | يصلح فقط لاحقاً لتفضيلات ترتيب الشركات؛ لا يحق له تعريف مكونات أو صلاحيات حرة خارج السجل المسموح في الكود.

الخلاصة: **السجل المركزي هو الحل الاحترافي الجوهري**. React Router تحسين ممكن فوقه لاحقاً، وليس بديلاً عنه. لا حاجة لترحيل إطار التوجيه الآن كي نحل المشكلة بأمان.

## قواعد الحوكمة

1. معرف `PageId` غير قابل للتغيير أو لإعادة الاستخدام. تغير اللغة أو العنوان لا يغير المعرف.
2. تغيير ترتيب القائمة تعديل عرض فقط؛ يجب ألا يعدل مسار الصفحة أو صلاحيتها أو مكونها.
3. كل صفحة جديدة تدخل السجل بمسؤول واضح، صلاحيات، أيقونة، عناوين باللغتين، ومعالجة حالة العرض.
4. لا يُكتب `window.location.hash` ولا `section=N` خارج مساعد تنقل واحد وملفات توافق الاختبار.
5. إيقاف صفحة يتطلب alias/redirect أو سجل إيقاف واضح، ولا يتم حذف رابطها بصمت.
6. تظل API وRLS/التفويض الخادمي مصدر قرار الوصول؛ إخفاء القائمة ليس تفويضاً أمنياً.

## خطة الترحيل المرحلية

### 0. جرد وتجميد (قصير)

- جرد كل `module + section`، الروابط الصلبة، حالات `stage`، الصلاحيات، اختبارات E2E، والروابط التي تصدرها API.
- إنشاء جدول تعيين ثابت: `module + legacy section → pageId`، مع مالك لكل صفحة.
- تجميد إضافة روابط أو قواعد وصول رقمية جديدة.

### 1. البنية التحتية والمسار المتوافق

- إنشاء `page-registry.ts` و`route-adapter.ts` و`navigate(pageId, state)`.
- يقبل المحلل `page` القانوني و`section` القديم؛ يرفض التعارض بينهما بدلاً من التخمين.
- عند فتح رابط قديم صحيح: يحلّه إلى `PageId` ثم يستخدم `history.replaceState`، من دون إنشاء سجل تاريخ إضافي، لتحويله للمسار القانوني.
- نقل التخزين المحلي والجلسة و«الأخيرة» إلى كتابة `PageId` مع قراءة صيغة v1 القديمة أثناء نافذة التوافق.

### 2. تجربة مالية تجريبية

- ترحيل صفحات المالية الخمس كاملة: التنقل، العناوين، الأيقونات، الصلاحيات، عرض المحتوى، الروابط العميقة، والتقارير الصادرة من الخادم.
- وضع `finance.settings` بترتيب أخير، مثلاً `order: 99`، لإثبات أن النقل المرئي لا يغير الهوية.
- لا ينتقل موديول آخر قبل نجاح بوابة القبول أدناه.

### 3. ترحيل الموديولات تباعاً

- ترحيل الموديولات بحسب روابطها المتبادلة والمخاطر، مع إبقاء محول التوافق عاماً.
- استبدال كل الروابط الداخلية بمساعد `navigate` وباني رابط مشترك يستخدمه الويب وواجهات API عند الحاجة.
- نقل عقد التقارير للتحقق من الرابط القانوني أثناء السماح المؤقت بالقديم، ثم جعل API يصدر القانوني فقط.

### 4. القياس وإيقاف التوافق

- إضافة قياس محدود للروابط القديمة التي حُلّت، والروابط غير المعروفة، ومحاولات الوصول غير المسموح.
- بعد دورتين إصدار على الأقل وعدم وجود استعمال معتبر للروابط القديمة، يحدد تاريخ إزالة القراءة القديمة عبر ADR منفصل.
- لا تحذف طبقة التوافق أو الاختبارات القديمة من دون بيانات تثبت أمان ذلك.

### 5. تحسين اختياري لاحق

- إن احتاج المنتج روابط متداخلة عامة أو تحميل بيانات عبر المسار أو مشاركة URL خارج التطبيق، يمكن نقل الناقل من Hash إلى React Router بعد استقرار السجل.
- تفضيلات ترتيب قائمة خاصة بشركة يمكن إضافتها من قاعدة البيانات فوق السجل المسموح، مع سجل تدقيق وحدود واضحة.

## بوابة القبول والاختبارات

لا تنتقل المرحلة التالية إلا بعد إثبات ما يلي:

- ترتيب صفحة في القائمة لا يغير `PageId` أو المكون أو الصلاحية أو وجهة الرابط.
- الرابط القانوني والقديم يفتحان الصفحة نفسها؛ وتحويل القديم لا يكرر التاريخ.
- الروابط من API تلتزم بالعقد، وتفتح الصفحة الصحيحة عند النقر.
- المستخدم غير المصرح له يصل إلى صفحة آمنة بديلة ولا يرى أو ينفذ المحتوى المحمي.
- العنوان العربي والإنجليزي، التنقل المحمول، لوحة المفاتيح، والصفحات الأخيرة تعمل بالمعرف الثابت.
- حالات `stage` صالحة فقط للصفحة المعنية؛ والسجل يعالج الرابط غير المعروف بأمان.
- اختبارات وحدة: فرادة المعرفات، الترجمتان، الترتيب، الصلاحيات، المحلل، وتحويل التخزين.
- اختبارات E2E: فتح مباشر، سابق/التالي، رابط قديم وجديد، رابط صادر من التقرير، صلاحيات، وإعادة ترتيب إعدادات المالية.
- فحص CI يمنع أي `section=` أو كتابة مباشرة للـhash خارج طبقة التوافق والمساعد المعتمد.

## المسؤولية ومقياس النجاح

يقود فريق المنصة/المعمارية السجل ومحول المسارات. يملك كل فريق موديول تعيين صفحاته واختباراتها. تراجع الجودة الفرق بين الروابط القديمة والجديدة، والواجهات المحمولة، والصلاحيات قبل كل انتقال.

ينجح المشروع عندما يصبح نقل عنصر في القائمة عملية عرض آمنة لا تمس الرابط أو الصلاحية أو المحتوى، وعندما تصدر كل الروابط العميقة من مصدر واحد موثق وقابل للاختبار.
