# أساس التفسير الموحد واستهلاك بصيرة

**التاريخ:** 2026-08-24
**الحالة:** معتمد للتنفيذ المرحلي — اكتملت E0–E4 وE5a وE5a.1 على قاعدة الاختبار المحلية؛ يبقى Pilot الحي تحت بوابته
**المالك:** منصة بصيرة، مع مالكي مركز القرار والتسويق

## النتيجة التي نبنيها

لا يصبح كل فتح شاشة طلباً إلى مزود الذكاء، ولا تبقى إجابة بصيرة داخل نافذة
واحدة ثم تضيع. ينشئ النظام، عند الحاجة فقط، **تفسيراً موحداً محفوظاً**
ومقيداً بدليل محدد. يمكن إظهاره في الحملة، التنبيه، مركز القيادة، أو تقرير
آخر من دون نسخ النص أو إعادة الاتصال بالمزود.

```text
قراءة رسمية / حزمة دليل مجمدة
              ↓
  مخطط استدعاء بصيرة الحتمي
  ├─ لا حاجة للذكاء: قراءة أو قاعدة أو جودة ناقصة
  ├─ تفسير صالح موجود: إعادة استخدام بلا تكلفة مزود
  ├─ محجوب: صلاحية أو بوابة أو حد استخدام
  └─ طلب يدوي مؤهل: استدعاء مزود واحد مقيد
              ↓
      تفسير موحد غير قابل للتعديل
              ↓
  مواضع عرض مرجعية فقط + تقييم بشري + قرار بشري منفصل
```

يبقى الحساب المالي والمقارنة والجودة والتنبيه حتمياً على الخادم. بصيرة تشرح
الدليل ولا تحسبه من الجداول ولا تنشئ حقيقة أو سببية أو فعل خارجي.

## تجربة المستخدم المعتمدة

- عند فتح التسويق أو مركز القرار أو الرسم: **صفر طلبات ذكاء**.
- تظهر القراءة الحتمية والجودة أولاً. إن كانت البيانات ناقصة أو لا تستحق
  شرحاً لغوياً، يظهر السبب بوضوح ولا يستدعى الذكاء.
- يختار المستخدم صراحة `فسّر الآن` عند وجود دليل صالح.
- إذا كان التفسير نفسه صالحاً، يظهر `تفسير محفوظ` ووقت إنشائه والدليل الذي
  بُني عليه، بدلاً من إعادة توليده.
- `تحديث التفسير` فعل صريح، ولا يصبح طلباً جديداً إلا إذا تغير الدليل أو
  اللغة أو نسخة المهارة/السياسة/السياق، أو اختار المستخدم سبب تحديث مقبولاً.
- ملاحظة المستخدم وقرار المدير يسجلان ككيانات بشرية مستقلة؛ لا
  يعيدان كتابة التفسير ولا يتحولان إلى بيانات مالية أو تعليمات للنموذج.

## الحدود والملكية

| الطبقة | تملك | لا تملك |
| --- | --- | --- |
| المالية والعمليات | الحقائق الرسمية والمستندات المتصالحة | تفسير الذكاء أو إسناد السبب |
| مركز القرار والسياق | القواعد والتنبيهات وحزم الأدلة | حملة أو بيانات Google أو نص التفسير |
| التسويق | الحملة ومواضع عرض القراءة | مبلغ فعلي مستقل أو محرك تنبيهات جديد |
| منصة بصيرة | اختيار الاستدعاء والتفسير والإيصال والتقييم | SQL حر، أدوات حرة، أو فعل خارجي |
| المستخدم | طلب شرح، تقييمه، وملاحظة/قرار منفصل لاحقاً | تغيير الدليل أو سياسة المهارة |

## مفتاح إعادة الاستخدام

إعادة الاستخدام **دقيقة وليست تشابهية** ولا تنتقل بين الشركات. يتكون
`reuseKey` من JSON مرتب المفاتيح ثم SHA-256 لهذه القيم:

```text
tenant + company + subject kind/id + skill/version + policy version
+ prompt/schema version + language + evidence checksum
+ approved company-context digest + system identity version + model profile
```

تغيّر أي عنصر جوهري ينتج مفتاحاً جديداً. لا يؤثر مكان العرض أو تصميم الواجهة
في المفتاح. لا يعاد تفسير منتهٍ أو فاشل أو تابع لشركة أخرى.

## نموذج البيانات المرحلي

### E1 — التفسير والطلب المتزامن

- `AiInterpretation`: مخرج AI ناجح فقط؛ مشفر، محكوم بفترة احتفاظ، له checksum
  ويرتبط بإيصال ناجح وحزمة دليل وبصمة إعادة الاستخدام. صف append-only.
- `AiInterpretationRun`: claim قصير العمر لمفتاح إعادة الاستخدام. يمنع طلبين
  متزامنين من الاتصال بالمزود. حالته تشغيلية (`PENDING`/`COMPLETED`/`FAILED`)
  وليست تفسيراً أو حقيقة أعمال.
- `AiInterpretationPlacement`: مرجع عرض فقط من تفسير واحد إلى حملة أو تنبيه
  أو مركز قيادة أو تقرير؛ لا ينسخ الناتج. بدأت مواضع الحملة والتنبيه في E2.
  لا ينشئ مجرد فتح مركز القيادة أو التقرير موضعاً جديداً؛ فالموضع يتطلب هدفاً
  موثقاً وفعل حفظ صريح في مرحلة لاحقة.

لا تحفظ هذه المرحلة Transcript أو Prompt خام أو محتوى بريد/Google. الناتج
المنظم نفسه يشفر في ظرف AES-GCM مستقل عن أسرار المزود، وتبقى في السجل
البصمة والإصدارات والمعرفات فقط.

### E2 — التكامل

- يقرأ شارح التنبيه دليل التنبيه المجمد أولاً ثم يبحث عن تفسير مطابق.
- تبني الحملة حزمة دليل **find-or-create** بالبصمة بدلاً من إدخال لقطة متطابقة
  في كل طلب.
- تضاف مواضع عرض للتنبيه والحملة؛ ويستطيع مركز القيادة قراءة المرجع نفسه.
- تستمر عقود الواجهات الحالية، مع حقول `interpretationId` و`disposition`
  لتوضيح هل الإجابة جديدة أو معاد استخدامها.

### E3 — مركز التفسيرات والإنسان في الحلقة

اكتملت كقسم سادس داخل **مركز القرار والسياق** باسم
`التفسيرات والقرارات البشرية`، وليس كموديول جديد. يقدم:

- `GET /administration/ai/interpretations` و`GET /administration/ai/interpretations/:id`
  لقراءة التفسير نفسه، بلا استدعاء مزود ولا إيصال جديد.
- تصفية كل تفسير بصلاحية مصدره: قارئ التنبيهات لا يرى الحملة لمجرد امتلاكه
  صلاحية بصيرة، والعكس صحيح.
- `AiHumanInsight` مشفراً ومنفصلاً (`NOTE`/`HYPOTHESIS`/`DECISION`) بدورة
  `DRAFT → APPROVED → REVOKED`. التصحيح يكون بسجل جديد يشير للسابق؛ لا تعديل
  للنص، ولا يدخل السجل إلى Prompt أو الحقيقة أو مفتاح إعادة الاستخدام. يفرض
  حاجز قاعدة البيانات أن التصحيح يتبع التفسير نفسه، ولا يسمح بإضافة أو تغيير
  معلومات الاعتماد أثناء السحب.
- روابط من التفسير في الحملة والتنبيه إلى المركز، مع فتح المصدر الأصلي، من
  دون نسخ النص أو تشغيل تفسير جديد. تتيح الواجهة إضافة السجل واعتماده أو
  سحبه، و«تصحيح بسجل جديد» بدل تحرير السجل السابق.

`COMMAND_CENTER` و`REPORT` موجودان في enum كقدرة مستقبلية فقط؛ لا يسمح E3
بإنشاء مواضع عامة لهما قبل وجود كيان هدف موثق وفحص خادمي له.

### E4 — حارس الاستهلاك والتكلفة

اكتملت طبقة E4 الأساسية محلياً للتفسيرين S2 فقط (التنبيه والحملة):

1. ملف كود-مملوك منخفض التكلفة: حد إدخال `12,000` token، حد مخرج `600`،
   reasoning منخفض، بلا أدوات، وبلا SDK retry خفي. قبل الاتصال يعدّ الخادم
   محلياً تعليمات بصيرة وJSON المجمد بترميز BPE المتوافق مع `gpt-5-mini`،
   ثم يضيف هامش تغليف ثابتاً مقداره `256` token؛ لا يوجد طلب مزود لحساب
   العدد. يتوقف العداد عند إثبات تجاوز الحد ولا ينشئ مصفوفة Tokens كاملة
   للحزمة المرفوضة. ملف العداد جزء من بصمة التفسير؛ تغييره لا يعيد استخدام
   نتيجة بنيت بحدود مختلفة.
2. `AiModelPriceRevision` مرقّم؛ البداية المقيدة هي `gpt-5-mini` فقط
   بسعر رسمي موثق في سجل السعر. إذا اختير نموذج بلا سعر معتمد، يفشل الطلب
   قبل الاتصال ولا يفترض سعراً.
3. قبل كل اتصال غير معاد الاستخدام ينشئ `AiBudgetReservation` داخل معاملة
   PostgreSQL مقفلة على يوم الرياض. يتحقق من حد المزود وعدد طلباته ومن حد
   الشركة/المهارة وعدد طلباتها، ثم يحجز أسوأ تكلفة مسموح بها.
4. بعد الاستجابة يسوي `AiUsageLedger` append-only التكلفة من usage الحقيقي؛
   عند غياب usage أو فشل/مهلة بعد احتمال وصول الطلب للمزود، يحتسب الحد
   المحجوز تحفظياً بدلاً من إخفاء تكلفة محتملة. المبلغ بالدولار لأن بطاقة
   السعر بالدولار؛ لا يخلط بسعر صرف متغير داخل الحارس.
5. يعرض المالك سقف المزود، ويحدد عند بدء تجربة المهارة سقفها اليومي وعدد
   طلباتها. لا يفعّل وجود مفتاح أو مهارة وحده أي اتصال، والتفسير المحفوظ
   لا يحجز ولا يستهلك.
6. مسارا «ملخص المالك» و«تحليل مرفقات البريد» اللذان كانا يستدعيان المزود
   مباشرةً مقفلان صراحةً إلى أن يُعاد بناؤهما فوق هذه البوابة. لا يستطيع
   متغير بيئة أو زر قديم تجاوز التفعيل أو الحصة أو سجل التكلفة.
7. لا يقبل السجل الخادمي اسم نموذج حر. المسارات المستقبلية (Gemini وQwen
   وDeepSeek) موثقة كقدرات مقفلة وبوابات فتح مرئية، ولا تملك مفتاحاً أو
   adapter أو سعراً أو مسار اتصال قبل اجتياز كل بوابة. تفاصيلها في
   `BASIRA_PROVIDER_CAPABILITY_REGISTRY_2026-08-24.md`.

القرار الحتمي قبل كل مسار S2 حي هو:

```text
عرض/رسم/تبويب أو دليل غير صالح → NO_AI (0 طلب، 0 حجز)
تفسير صالح مطابق                 → REUSE (0 طلب، 0 حجز)
طلب يدوي صالح + تحت السقف         → RESERVE → CALL → SETTLE
تجاوز سقف/سعر مجهول/حمولة كبيرة   → BLOCKED قبل الاتصال
```

لا يزال التوسيع التالي مؤجلاً: حصص شهرية وتنبيهات 50/80/90%، طابور موزع
ومصالحات Usage/Costs الخارجية، وسقف منصة مستقل. لا نوصف هذه العناصر بأنها
منفذة، ولا نفعّل تحليلاً تلقائياً قبلها وقبل E5.

### E5 — التقييم والإصدارات

التقييم ليس تعلماً آلياً. تتحول عينة مراجعة بشرية إلى حالات عربية مجمدة، ثم
تختبر نسخة مهارة/سياسة جديدة offline وshadow، ثم Pilot محدود، ثم Active
بقرار لجنة. تشمل المعايير: صحة الرقم، اكتمال الدليل، العربية، عدم ادعاء
السببية، مقاومة حقن التعليمات، الكلفة والزمن ونسبة إعادة الاستخدام.

اكتملت E5a الآن كحاجز **offline بلا اتصال مزود**:

1. يوجد كتالوج حالات عربية مملوك للكود للمهارتين المنفذتين S2 فقط: محلل
   مركز القرار ومحلل الأداء التسويقي. يغطي الدليل المتجمد، جودة البيانات
   الناقصة، منع السببية، منع الأفعال، عدم تحويل الناقص إلى صفر، وحقن
   التعليمات من النصوص غير الموثوقة.
2. تشغيل «فحص الجاهزية» من حوكمة بصيرة لا يقرأ بيانات الشركة، ولا يحجز
   ميزانية، ولا يتصل بالمزود. يسجل فقط نتيجة الضوابط وبصمة المجموعة في
   `AiSkillEvaluationRun` append-only ومعزولاً بـRLS.
3. لا يمكن بدء تجربة شركة لمهارة S2 حتى تجتاز الشركة نسخة مجموعة التقييم
   المطابقة للمهارة والسياسة. كما تبقى بوابة الخادم المنفصلة مطلوبة؛ اجتياز
   الفحص لا يفتح اتصالاً ولا يفعّل مهارة وحده.
4. لا نسمّي هذا اختبار جودة للنموذج ولا Shadow حياً. مرحلة E5b التالية
   تتطلب عينات مخرجات حقيقية ومُراجعة بشرية وميزانية محددة قبل اعتماد Pilot
   أو تغيير حالة مهارة إلى `ACTIVE`.

### E5a.1 — بوابة جاهزية التحليل الموحدة

اكتملت بوابة قراءة خادمية واحدة باسم `AnalysisReadiness`، وهي ليست شاشة أو
مصدر بيانات موازياً. تستمد حكمها من قراءة التنبيه المجمدة أو تحليل الحملة
الرسمي، ثم تعيده بعقد واحد:

- الحالات: `READY` و`BLOCKED` و`NEEDS_REVIEW`.
- تعرض سبباً عملياً وخطوة تالية، مثل: لا يوجد تنبيه موثق، بصمة الدليل غير
  سليمة، فترة الحملة ناقصة، مقارنة المبيعات غير جاهزة، أو مصروف الحملة غير
  مثبت/غير جاهز.
- تظهر كبطاقة صغيرة في التنبيهات والتسويق وتفاصيل الحملة؛ لا توجد لوحة جديدة
  أو درجة مضللة.
- يستدعي مسارا S2 الحيان البوابة نفسها **قبل** إنشاء مفتاح idempotency أو
  حجز ميزانية أو فك مفتاح المزود أو الاتصال به. أي حالة غير `READY` توقف
  الطلب محلياً.
- البطاقة نفسها لا ترسل بيانات إلى المزود ولا تنشئ تفسيراً أو إيصالاً.

المسارات المقصودة هي:

```text
قراءة/تنبيه أو تحليل حملة رسمي
              ↓
       AnalysisReadiness (خادم)
        ├─ BLOCKED / NEEDS_REVIEW → السبب والخطوة التالية، 0 طلب ذكاء
        └─ READY → طلب يدوي → reuse أو reserve → provider
```

| المرحلة | التسليم | الحالة | بوابة القبول |
| --- | --- | --- | --- |
| E0 | هذا القرار والعقود ومصفوفة الاختبار | مكتملة | موافقة المعمارية/الأمن/المنتج |

| E3 | مركز التفسيرات والملاحظات البشرية | مكتملة محلياً | لا نسخ نص ولا مزج ملاحظة بحقيقة أو Prompt |

| E5b | مراجعة مخرجات/Shadow/Pilot/Active | مؤجل | عينة بشرية، ميزانية مستقلة، وقرار لجنة |

## معايير القبول للدفعة الحالية

- لا يحدث اتصال بمزود الذكاء عند تحميل أي شاشة أو رسم أو تبويب.
- نفس الدليل مع نفس المهارة والسياسة واللغة والسياق يعيد نتيجة واحدة، حتى مع
  مفتاح idempotency مختلف.
- طلبان متزامنان لنفس البصمة ينشئان طلب مزود واحداً فقط؛ الثاني يتلقى حالة
  آمنة أو النتيجة الجاهزة، ولا ينشئ نسخة موازية.
- لا يعاد استخدام تفسير بين tenant أو شركة أو لغة أو دليل أو سياسة مختلفة.
- مخرج التفسير مشفر ومؤرخ وقابل للقراءة فقط بصلاحية المجال، بينما يبقى
  الإيصال والتفسير immutable.
- لا يرسل دليل ناقص/قديم/متعارض إلى المزود؛ يعرض النظام سبب المنع.
- تستخدم واجهات التنبيه والتسويق والمسار الحي عقد جاهزية واحداً؛ لا تعتمد
  الواجهة وحدها على تعطيل زر أو على حساب مالي مكرر.
- تظل واجهات التنبيه والحملة متوافقة، ويظهر فيها بصدق: جديد أو محفوظ أو
  محجوب، من دون زر وهمي.
- فتح مركز التفسيرات أو إضافة/اعتماد/سحب سجل بشري لا ينشئ `AiExecutionReceipt`
  ولا يتصل بمزود الذكاء.
- يرتبط كل سجل بشري بتفسير من الشركة نفسها، ومحتواه مشفر وثابت بعد الإنشاء؛
  لا يصحح إلا بسجل جديد أو سحب مدقق.
- لا ينشأ `AiBudgetReservation` أو `AiUsageLedger` عند فتح شاشة، أو نتيجة
  قاعدة حتمية، أو جودة غير صالحة، أو تفسير معاد الاستخدام.
- يتطلب أي اتصال حي سقف دولار يومياً محدداً للمزود **وللمهارة في الشركة**؛
  السعر غير المعتمد أو تجاوز السقف يمنع الاتصال قبل خروج الطلب.
- دفتر الاستهلاك والحجز معزولان بـRLS/FORCE RLS، والسجل append-only، بينما
  يطبق حد اليوم في `Asia/Riyadh` لا في توقيت خادم API.

## لجنة المراقبة

تراجع اللجنة التنفيذ مقابل هذا المخطط في بوابات E1 وE2 وE4:

- معماري النظام: العزل، البصمة، العلاقات وimmutability.
- أمن وخصوصية الذكاء: التشفير، الاحتفاظ، عدم تسريب Prompt/محتوى حساس.
- مالك المالية/التسويق: دلالة الدليل وعدم خلط الصرف أو المبيعات أو السببية.
- جودة واختبارات مستقلة: التوازي، RLS، invalidation، regression، وعدم
  الاتصال عند العرض.
- مالك المنتج: وضوح التجربة اليدوية وقيمة إعادة الاستخدام للمستخدم.

لا يبدأ التحليل التلقائي أو الموصلات أو أي فعل خارجي بهذه الوثيقة. أي تغيير
في هذا الحد يحتاج قراراً مستقلاً ومراجعة اللجنة.
