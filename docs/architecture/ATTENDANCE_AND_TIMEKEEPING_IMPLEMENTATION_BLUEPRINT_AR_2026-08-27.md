# مخطط بناء الحضور والانصراف وساعات العمل

**الحالة:** أساس التنفيذ قيد البناء — لا تغيّر مالي تلقائي.  
**النطاق:** Baseer ERP → الموارد البشرية → فرع ARZ Lounge في المرحلة الأولى.  
**قرار المنتج:** الحضور نظام إثبات حضور، احتساب وقت، رقابة وتسوية إدارية. لا ينشئ خصماً أو أجراً إضافياً تلقائياً من البصمات الخام. واجهة الموظف PWA فقط؛ لا حساب مستخدم، ولا كلمة مرور، ولا ربط جهاز. يستخدم الموظف PIN حضور من 4 أرقام يُدار من ملفه في HR ولا يُخزّن أو يعرض كنص صريح.

## 1. لجنة المراجعة وقرارها

| المراقب | القرار الملزم |
| --- | --- |
| المنتج والسياسات | فصل البصمات الخام عن الوقت المحتسب وعن القرار المالي؛ لا أوفر تايم تلقائي. |
| المعمارية | وحدة مستقلة باسم `attendance` ضمن ERP، وليست امتداداً لخدمة الرواتب أو `HrService`. |
| الواجهة وتجربة المستخدم | واجهات HR موحدة، عربية أولاً، وجوال أولاً، باستخدام مكونات Baseer الحالية فقط. |
| الأمن والخصوصية | QR قصير العمر + موقع لحظي + PIN مشفّر، بلا تتبع مستمر وبلا تخزين بصمات أو ربط جهاز. |
| الجودة | لا إطلاق قبل اختبارات حساب الوقت، التفويض، التزامن، QR/location، RTL والجوال، واختبار تجريبي فعلي. |

المسار المعتمد:

```text
بصمة حضور/انصراف موثقة
        ↓
احتساب يومي وشهري وفق وردية وسياسة مؤرخة
        ↓
استثناء أو قرار إداري بشري
        ↓
عند الحاجة فقط: إصدار خصم إداري من شاشة الحضور
        ↓
سجل الخصم القائم في HR، ويظل اختياره في مسير الراتب يدوياً
```

لا تكتب وحدة الحضور في مسير الرواتب، ولا تعدّل راتب الموظف أو أحداث الحضور الخام.

## 2. نطاق المرحلة الأولى

### ضمن النطاق

- فرع واحد: `ARZ Lounge`، نقطة جغرافية فعلية، نطاق ابتدائي 100م، وحد دقة موقع قابل للإعداد.
- ورديات أسبوعية ثابتة، مع تصميم يقبل وردية عابرة لمنتصف الليل لاحقاً.
- حساب موظف مرتبط بسجل الموظف وهاتف واحد معتمد.
- حضور وانصراف متصل بالإنترنت: جلسة موثوقة، تحقق محلي للجهاز، موقع لحظي، ومسح QR متغير داخل الفرع.
- تقارير يومية وشهرية للساعات المستهدفة والمحتسبة، التأخر، الخروج المبكر، النقص، والوقت الزائد المرشح.
- طلبات استثناء، مراجعة شهرية، وإصدار خصم إداري يدوي من داخل الحضور.
- سجل تدقيق دائم؛ لا حذف ولا تعديل للوقت الخام.

### خارج النطاق

- خصم تلقائي أو إضافة أجر إضافي تلقائية.
- تتبع موقع أثناء الدوام، أو استخدام GPS خارج لحظتي الحضور والانصراف.
- عمل دون إنترنت أو قائمة انتظار مؤجلة.
- ZKTeco، RFID، أو أي جهاز خارجي في المرحلة الأولى.
- احتساب راتب بالساعة أو استبدال دورة الرواتب الحالية.

## 3. سياسة الوقت المعتمدة مبدئياً

| المصطلح | المعنى |
| --- | --- |
| الوقت الخام | وقت الخادم عند العملية؛ لا يتبدل أبداً. |
| وقت الوردية | بداية ونهاية واستراحة محددة في إصدار السياسة. |
| مهلة السماح | حكم انضباطي لا يغير الوقت الخام. |
| الوقت المحتسب | وقت العمل بعد الاستراحة والقواعد. |
| وقت زائد مرشح | وقت خارج الوردية لم يعتمد كأوفر تايم. |
| أوفر تايم معتمد | وقت إضافي اعتمده المالك أو مدير الشركة مع سبب؛ تقرير فقط في V1. |
| نقص وقت | فرق محتسب يحتاج قراراً، لا خصماً تلقائياً. |

مثال وردية 9:00 ص–4:00 م، بعد تعريف الاستراحة صراحة:

| البصمات | النتيجة الافتراضية |
| --- | --- |
| 8:45 / 4:00 | حضور كامل؛ دخول مبكر خام، لا أوفر تايم. |
| 9:00 / 4:15 | حضور كامل؛ خروج متأخر خام، لا أوفر تايم. |
| 8:45 / 4:15 | وقت مبكر ومتأخر ظاهر للمراجعة، وليس 30 دقيقة مدفوعة تلقائياً. |
| 9:08 مع سماح 10 دقائق | الوقت الخام 9:08 محفوظ؛ ضمن السماح انضباطياً. |
| 9:15 / 4:15 | تأخر وخروج متأخر؛ لا تقاص تلقائي بينهما. |

أي وقت خارج الوردية لا يصير أوفر تايم إلا عند ثبوت عمل فعلي وتكليف/اعتماد. وينبغي تثبيت الاستراحة، والسماح، وعتبة الوقت الزائد (مقترح 30 دقيقة) في لائحة العمل والعقد قبل ترتب خصم أو استحقاق. القواعد السعودية لساعات العمل والراحة والأجر الإضافي هي حد نظامي أعلى من إعدادات التطبيق؛ راجع [المنصة الوطنية](https://my.gov.sa/en/content/employment) و[وزارة الموارد البشرية](https://www.hrsd.gov.sa/id/node/5557745).

## 4. الصلاحيات

| الفاعل | ما يملكه |
| --- | --- |
| المالك | كامل التحكم على مستوى المستأجر، كما هو قائم، مع عدم القدرة على حذف الحدث الخام. |
| مدير الشركة | كامل التحكم في وحدة الحضور لشركته فقط: الإعدادات، المراجعة، الخرائط، الإغلاق، الاستثناءات وإصدار الخصم. |
| الموظف | تسجيل ذاته، رؤية ورديته وسجله فقط، وتقديم طلب استثناء؛ لا يرسل `employeeId` في طلب التسجيل. |

تضاف قدرات مستقلة: `attendance.self.read`, `attendance.self.capture`, `attendance.self.exceptions.write`, `attendance.read`, `attendance.manage`, `attendance.review`, `attendance.deductions.issue`, `attendance.qr.manage`, `attendance.reports.read`.

لا يكفي منح capability: مسارات الإدارة وإصدار الخصم تتحقق خادمياً أيضاً أن المستخدم هو المالك أو يحمل دور `BASEER_COMPANY_MANAGER`. لا تمنح الصلاحيات الإدارية لأدوار مخصصة أخرى. كل تصحيح أو إعادة فتح أو اعتماد يسجل باسم صاحبه وسببه.

## 5. بنية البيانات المقترحة

تضاف هذه النماذج إلى مخطط Prisma، وكلها تحمل `tenantId` و`companyId` وعلاقات مركبة وعزل الشركة كما في بقية HR:

| النموذج | المسؤولية |
| --- | --- |
| `AttendanceBranch` | الفرع، النقطة، النطاق، حد الدقة، والمنطقة الزمنية. |
| `AttendancePolicyVersion` | قواعد مؤرخة: الاستراحة، السماح، الحد الأدنى للوقت الزائد وقواعد الوردية. لا تعدل النسخة التاريخية. |
| `AttendanceShift` و`AttendanceEmployeeShiftAssignment` | قالب الوردية والتعيين المؤرخ للموظف. |
| `AttendanceEmployeeUserLink` | ربط مستخدم واحد نشط بسجل موظف، بموافقة مدير. |
| `AttendanceDeviceLink` | هاتف/مفتاح جهاز مسجل وحالته؛ لا يعد معرّف الجهاز وحده إثباتاً. |
| `AttendanceQrTerminal` و`AttendanceQrChallenge` | كشك QR وتحدٍ موقع قصير العمر، يخزن digest لا القيمة المكشوفة. |
| `AttendanceEvent` | حضور/انصراف خام append-only: وقت الخادم، الموقع، accuracy، المسافة، الجهاز، QR، وطريقة التحقق. |
| `AttendanceWorkSession` | جلسة مشتقة تربط الحضور بالانصراف وحالتها. |
| `AttendanceDailySummary` | ملخص قابل لإعادة البناء بالدقائق: مستهدف، محتسب، تأخر، نقص، وقت زائد مرشح ومعتمد. لا يحمل مبلغاً مالياً. |
| `AttendanceException` | طلب وتصنيف وقرار الاستثناء، من دون تغيير الحدث الأصلي. |
| `AttendanceDeductionIssue` | مرجع واحد موثق بين قرار حضور وخصم إداري HR؛ يمنع التكرار. |

## 6. معمارية الخدمة والتكامل

```text
apps/api/src/attendance/
├─ attendance.controller.ts
├─ attendance-access.service.ts
├─ attendance-capture.service.ts
├─ attendance-qr.service.ts
├─ attendance-policy.service.ts
├─ attendance-review.service.ts
├─ attendance-reports.service.ts
├─ attendance-deduction-bridge.service.ts
├─ attendance-evaluation.ts       # دوال حساب نقية
└─ attendance-geo.ts              # distance/accuracy
```

- العقود في `packages/contracts/src/attendance.ts`، ومسار HTTP هو `/attendance/...`.
- لا يزداد حجم `hr.controller.ts` أو `hr.service.ts` العام؛ تبقى الحضور وحدة مستقلة ضمن modular monolith.
- واجهة الويب: `attendance-client.ts`، مساحة عمل lazy باسم `hr-attendance`، وقاموس نصوص `attendance-copy.ts`.
- كل كتابة تتم داخل `DatabaseService.inTenantTransaction`، مع `IdempotencyService` و`pg_advisory_xact_lock` على الشركة/الموظف/يوم العمل.
- يفرض migration فهرساً جزئياً يمنع أكثر من جلسة عمل مفتوحة للموظف، ولا تعتمد سلامة الحالة على الواجهة.

### زر «إصدار خصم إداري»

هو أمر بشري من شاشة المراجعة، لا قاعدة آلية:

```text
تسوية حضور مغلقة
→ زر إصدار خصم
→ نافذة: مبلغ قابل للتعديل + سبب وملاحظة إلزاميان
→ تأكيد
→ AttendanceDeductionBridgeService
→ HrEmployeeAdministrativeDeduction + AttendanceDeductionIssue + AuditEvent
```

ينشأ الخصم ومرجعه في معاملة واحدة. لا يستدعي attendance أي controller داخلياً؛ يستخرج أمر HR مشترك `createInTransaction` من خدمة الخصومات لكي يستخدمه الجسر بأمان. يظهر رقم `DED-...` في الحضور وفي قسم السلف والخصومات، لكنه **لا يضاف تلقائياً** لمسير الرواتب؛ يظل اختيار الخصم في مسير الراتب قراراً قائماً.

## 7. التحقق الأمني ومسار التسجيل

```text
الجلسة + رابط الموظف + رابط الجهاز
→ تحقق محلي للجهاز
→ موقع لحظي دقيق
→ مسح QR قصير العمر
→ تحقق خادمي من الحالة والفرع والمسافة والدقة
→ حفظ الحدث والجلسة والتدقيق في معاملة واحدة
```

- QR صالح لعدة موظفين في نافذته، ولا يستهلك عالمياً عند أول مسح. يمنع إعادة العملية نفسها للموظف نفسه.
- الوقت من الخادم، وليس ساعة الهاتف.
- يفحص الخادم QR وتوقيعه وانتهاءه والفرع، ونوع الحدث المتوقع، والجلسة المفتوحة، والمسافة وaccuracy.
- `mockLocationStatus` إشارة خطر للمراجعة لا إثبات قاطع للعقوبة.
- لا تخزن بصمة أو صورة وجه؛ تخزن طريقة نجاح التحقق فقط (`LOCAL_BIOMETRIC` أو `APP_PIN`).
- الإحداثيات الدقيقة لا تكرر في `AuditEvent` أو رسائل خطأ الواجهة؛ تبقى في حدث الحضور بصلاحية المالك/مدير الشركة فقط.
- كشك QR يملك جلسة منخفضة الامتياز لا تصل إلى بيانات HR أو الإدارة.

## 8. خريطة الواجهات

| الواجهة | الهدف |
| --- | --- |
| بوابة الموظف | زر سياقي واحد: حضور أو انصراف، وردية اليوم، آخر عملية بتوقيت الخادم، طلب استثناء. |
| رحلة التحقق | تحقق محلي، صلاحية الموقع، فحص الجودة، الكاميرا ونتيجة مفهومة مع إعادة محاولة. |
| شاشة QR للكشك | رمز عالِ التباين، عداد انتهاء، وقت خادم وحالة اتصال؛ بلا بيانات شخصية. |
| لوحة اليوم | للمالك/المدير: حاضر، متأخر، لم يسجل، في الدوام، انصرف، واستثناءات. |
| ملف حضور الموظف | الخام، الملخص، الاستثناءات، والخصم المرجعي؛ لا تحرير للحدث الخام. |
| المراجعة الشهرية | المجاميع، الإغلاق، الوقت الزائد المرشح/المعتمد، وإصدار الخصم عند اللزوم. |
| الإعدادات | الفرع والموقع، QR، السياسات، الورديات والجداول. |

تعاد استخدام `BaseerWorkspace`, `BaseerCard`, `BaseerButton`, `BaseerDataGrid`, `BaseerStatusBadge`, `BaseerFormDialog` والحقول المشتركة. العربية هي الافتراضية؛ النصوص في قاموس `ar/en`، والأوقات والمعرفات والمبالغ في `bdi/dir=ltr` عند الحاجة. لا يُعرض اللون كدليل وحيد، وتظهر النتائج عبر `aria-live`، وزر التسجيل لا يقل عن 44×44px.

## 9. مراحل التسليم ومعابر القرار

| المرحلة | التسليم | شرط الانتقال |
| --- | --- | --- |
| A0: سياسة وتشغيل | تعريف الاستراحة، الوردية، السماح، الاستثناءات، الخصوصية، ونصوص القرار. | اعتماد المالك والمدير للسياسة وعدم وجود أثر مالي تلقائي. |
| A1: الأساس الآمن | الربط مستخدم/موظف/جهاز، QR، الموقع، الأحداث الخام، شاشة الموظف والكشك. | تحقق API/RLS والتزامن وPilot بلا رواتب. |
| A2: تقييم الوقت | الوردية، الحساب بالدقائق، لوحة اليوم، التقارير، الاستثناءات. | مراجعة حالات واقعية لمدة أسبوعين على الأقل. |
| A3: المراجعة والخصم | إغلاق شهري، اعتماد وقت إضافي تقريري، زر إصدار الخصم مع المرجع المتبادل. | مطابقة الخصم في HR ومنع تكراره، دون اختيار آلي في المسير. |
| A4: التقييم والتوسع | قياس GPS/QR والاستثناءات، ثم قرار ZKTeco/RFID أو قائمة انتظار آمنة أو استحقاق OT مالي لاحق. | موافقة محدثة بعد نتائج التشغيل الفعلية. |

## 10. الاختبارات وبوابات الجودة

### اختبارات لا تقبل الاستثناء

- وحدات الحساب: استراحة، سماح، دخول/خروج مبكر ومتأخر، نقص، عبور منتصف الليل، إجازة ويوم راحة ومنطقة زمنية.
- وحدات الأمن: Haversine، حد accuracy، توقيع وانتهاء QR، تدوير challenge، وmock-location signal.
- الخدمة والتكامل: شركتان، مستخدم بلا رابط موظف، هاتف غير معتمد، QR منتهٍ، replay، حضوران متزامنان، خروج بلا حضور، ومفتاح idempotency مكرر أو مخالف.
- RBAC: الموظف لا يقرأ زميلاً أو خريطة أو إعدادات أو خصماً؛ المالك/المدير فقط ينجحان إدارياً.
- خصم من الحضور: ينشئ خصماً واحداً ومرجعاً متبادلاً في معاملة واحدة، ويظهر في وحدة HR، ولا يظهر في مسير الراتب إلا عند اختياره يدوياً.
- E2E مرئي: عربي/إنجليزي، هاتف/سطح مكتب/كشك، نجاح وفشل صلاحيات الكاميرا وGPS وQR والإنترنت، accessibility ولوحة المفاتيح وقارئ الشاشة.

### بوابات الإصدار

1. مراجعة معمارية: schema، migrations، معاملة جسر الخصم، RLS والصلاحيات والتدقيق.
2. مراجعة أمنية: threat model للـQR والموقع والجهاز، واختبارات تجاوز التفويض وreplay والتزامن.
3. مراجعة UX: تجربة فعلية على Android وiPhone، RTL، وموظف غير تقني.
4. QA: `check:architecture`, `check:permissions`, `check:hr-rls`, فحوص TypeScript، اختبارات HTTP/DB الجديدة، E2E وaccessibility خضراء.
5. Pilot: ARZ فقط، نحو 15 موظفاً، أسبوعان إلى شهر، بلا خصم أو أوفر تايم مالي آلي.

## 11. قرارات معلقة قبل A0

- هل الاستراحة مدفوعة أم غير مدفوعة، وما توقيتها ومدتها؟
- ما مهلة السماح وعدد مرات استعمالها شهرياً؟
- ما عتبة الوقت الزائد الذي يستحق المراجعة؟
- ما قاعدة موظفي الافتتاح والإغلاق؟
- متى يصبح النقص قابلاً للخصم ومتى يعامل كاستثناء؟
- ما مدة الاحتفاظ ببيانات الموقع، ومن يحق له رؤية الخريطة؟
- هل نستخدم تطبيقاً جوالاً مغلفاً native shell لتحقيق تحقق أقوى من الجهاز والموقع، أم نبدأ بـPWA مع توثيق حدوده؟

لا يبدأ A1 قبل إقفال هذه القرارات خطياً.
