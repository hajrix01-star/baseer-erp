# قرار المنتج والأمن: مساعد بصير الذكي

**الحالة:** معتمد للتصميم والبنية الخلفية؛ واجهة المحادثة والتنفيذ الفعلي مرحلتان لاحقتان.

## القرار

يُضاف إلى BASEER ERP مساعد داخلي باسم افتراضي **مساعد بصير** (`Baseer Assistant`). الاسم عربي/إنجليزي مركزي على مستوى نظام BASEER ERP داخل الـtenant، وليس اسمًا مختلفًا لكل شركة. يملك مسؤول الإدارة صلاحية إنشاء نسخة جديدة من الاسم والنبرة وتعليمات السلامة؛ لا تُعدّل النسخة السابقة بل تؤرشف، مع سجل تدقيق وإعادة تشغيل آمنة للطلب.

لا يعني الاسم المركزي اختلاط بيانات الشركات: كل محادثة، سؤال، مصدر بيانات، إجابة، وصلاحية عمل تبقى ضمن الشركة النشطة وسياق المستخدم الحي.

## تجربة المستخدم المعتمدة

يظهر زر محادثة عائم في الواجهة لاحقًا. عند فتحه، يعرف المساعد تلقائيًا الشركة النشطة، الشاشة/الموديول، الفترة المختارة، واللغة، من الخادم فقط. لا يعتمد على companyId أو صلاحيات يكتبها المستخدم داخل الرسالة.

الإجابة المهنية تتكون من:

1. نتيجة مختصرة ومباشرة.
2. الأدلة الرقمية ومصدرها وتاريخ حداثتها.
3. الأسباب أو الفرضيات، مع تمييز «ارتباط زمني» عن «سبب مثبت».
4. النواقص أو البيانات غير المكتملة بدل اختراع رقم أو تفسير.
5. اقتراحات قابلة للمراجعة وروابط داخلية للتفصيل؛ لا تنفيذ تلقائي.

مثال سؤال: «لماذا الحملة ضعيفة؟» يعيد قراءة صالحة ومفلترة لأداء الحملة، الفترة السابقة، حالة اكتمال مبيعات ERP وGoogle Ads وGoogle Business، ثم يذكر المؤشرات التي تغيّرت. لا يدّعي أن الإعلان سبّب تغير المبيعات من دون منهج إسناد موثق.

## حدود الإصدار الأول

المساعد **للقراءة والتحليل وصناعة المسودات فقط**:

- يشرح مؤشرات المالية والتسويق بعد أن تتوفر read models الرسمية.
- يقترح مسودة رد على تقييم Google، لكنه لا ينشرها.
- لا ينشئ قيدًا، فاتورة، دفعة، أو تعديلًا ماليًا.
- لا ينشئ/يعدل/يوقف Google Ads، ولا يغيّر ميزانية أو إنفاقًا.
- لا ينشر ردًا أو منشورًا أو رسالة خارجية تلقائيًا.
- لا يملك SQL حرًا أو ملفات النظام أو تصفح ويب مفتوح أو API عامة.

أي فعل مستقبلي يكون أمرًا منفصلًا خارج المحادثة: معاينة، تأكيد صريح من شخص مخوّل، idempotency، تدقيق، وسجل نتيجة. بالنسبة لردود Google: منشئ المسودة لا يساوي المعتمد أو الناشر، ولا يوجد نشر آلي في هذه المرحلة.

## البنية الخلفية

يوجد مزود ذكاء واحد مركزي للنظام كله، قابل للتبديل بين adapters معتمدين. الإعدادات لا تُخزّن في المتصفح؛ مفتاح المزود مشفّر في الخادم فقط. يظل استخدام كل شركة محاسبًا ومنعزلًا عنها.

مهارات الإصدار الأول محددة بإصدار ونطاق، وليست «ذكاءً عامًا»:

- إرشاد محاسبي وقراءة فقط.
- تحليل الأداء التسويقي.
- تحليل Google Ads.
- تحليل Google Business والسمعة وصياغة مسودة الرد.
- تحليل تنفيذي لمركز القيادة.

كل مهارة تستخدم أدوات قراءة ضيقة بعقود خادمية، مثل ملخص أداء حملة أو حقائق Google اليومية أو قراءة مالية مجمعة. المرفقات، نصوص التقييمات، ووصف الحملات تعامل كبيانات غير موثوقة ولا تستطيع تغيير تعليمات المساعد.

## الخصوصية والحوكمة

- CompanyContext وRBAC يتحققان في كل رسالة وكل أداة قراءة.
- الحد الأدنى من البيانات فقط يرسل للمزود؛ لا أسرار، OAuth tokens، قيود أو فواتير خامة، أو بيانات عملاء/موظفين غير لازمة.
- تدقيق محفوظ: المستخدم، tenant/company، المهارة، نسخة السياسة/المزود/النموذج، correlation ID، الوقت، التكلفة والحالة. لا يسجل النص الخام للمحادثة في AuditEvent.
- إن حُفظ تاريخ المحادثة لاحقًا، يكون مشفرًا، company-scoped، قصير الاحتفاظ (30 يومًا افتراضيًا) وقابلًا للحذف وفق السياسة.
- kill switch، rate limits، سقف طلبات/تكلفة، timeout وcircuit breaker إلزامية.

## ترتيب التنفيذ

1. تثبيت الهوية المركزية والـAI Gateway والمهارات المقيدة — منفذ في البنية الخلفية الأولية.
2. عقود جلسات المحادثة والرسائل والمصادر/الاقتباسات وإيصالات الأدوات، مع اختبارات العزل وحقن التعليمات والاحتفاظ.
3. بناء read models رسمية لكل مجال، ويبدأ بالتسويق بعد وصول حقائق الحملات وGoogle ومبيعات ERP المعتمدة.
4. Adapter فعلي لمزود واحد بعد قرار مزود/منطقة معالجة/احتفاظ منفصل؛ يبقى قابلًا للاستبدال.
5. زر المحادثة العائم وواجهة الإدارة، بعد اجتياز اختبارات الصلاحيات وعدم وجود أثر جانبي.

لا يُبنى زر جميل قبل توفر هذه العقود والمصادر؛ وإلا لن يستطيع الإجابة بأدلة موثوقة.
