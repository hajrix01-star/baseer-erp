# قرار متانة الجلسة والعامل الخلفي

**الحالة:** معتمد — 2026-08-21
**المالك:** معمارية Baseer ومالكو الهوية وتشغيل API

## الحادثة التي يمنعها هذا القرار

كانت شاشة الدخول تعرض «تعذر تسجيل الدخول. تحقق من بياناتك…» لحالتين لا
تتعلقان ببيانات المستخدم:

1. رمز الوصول JWT ينتهي بعد 15 دقيقة، فيما الخادم يصدر رمز تجديد صالحاً
   30 يوماً. الواجهة كانت تحفظ رمز الوصول فقط، ثم تمسح الجلسة عند أول `401`.
2. عامل استيراد السياق بدأ تلقائياً داخل كل API. كان يمسك transaction لقفل
   advisory ثم يفتح معاملات مستأجرين داخله؛ وهذا أدى إلى `P2028 Transaction
   not found` وإعادة تشغيل عملية API في التشغيل المحلي.

الرسالة العامة كانت تخفي أيضاً فشل فتح الشركات المتاحة بعد نجاح تسجيل
الدخول، فيبدو فشل البنية التحتية كأنه خطأ كلمة مرور.

## قواعد الجلسة

- الجلسة في الويب هي زوج: `accessToken` و`refreshToken`، مع
  `sessionExpiresAt` والشركة النشطة؛ رمز الوصول وحده ليس جلسة صحيحة.
- يخزن الزوج في `sessionStorage` للمتصفح فقط. لا يكتب في `localStorage` ولا
  في URL ولا في سجل تشخيصي.
- عند `401` من طلب محمي، يجدد منسق جلسة موحد الرمز مرة واحدة وبطلب مشترك
  (single-flight)، ثم يعيد **الطلب الأصلي مرة واحدة فقط**.
- فشل الشبكة أو `5xx` أثناء التجديد لا يمسح الجلسة. يسجل التطبيق خطأ الخدمة
  ويتيح إعادة المحاولة. تمسح الجلسة فقط إذا رفض endpoint التجديد نفسه بـ`401`
  أو رفض الرمز الجديد مرة أخرى بـ`401`.
- دوران refresh token يظل ملك الخادم. لا تطل مدة access token لعلاج مشكلة
  التكامل، ولا يحاول العميل تدوير token بنفسه.
- شاشة الدخول تفرق بين: بيانات دخول مرفوضة، نجاح الدخول مع فشل فتح مساحة
  العمل، وتعذر الخدمة. لا تعرض سبباً داخلياً أو token أو correlation ID.

## قواعد العامل الخلفي

- أي عامل دوري opt-in صريح عبر متغير بيئة. API العادي لا يشغل استيراداً أو
  بحثاً دورياً من تلقاء نفسه.
- تعيين عامل واحد في النشر مستحب؛ ومع ذلك تستعمل النسخ المتعددة lease قصير
  المدة في جدول `SystemSchedulerLease` لمنع التنفيذ المتزامن.
- لا يلف lease callback داخل Prisma interactive transaction. يحصل العامل على
  lease قصير، ثم ينفذ أعمال المستأجرين في معاملات معزولة، ثم يحرر lease في
  `finally`. عند crash تنتهي مدة lease ويمكن لمحاولة لاحقة استلامها.
- callback الخاص بـ`setTimeout` و`setInterval` يلتقط الخطأ ويسجل رسالة آمنة؛
  لا يسمح بوعد مرفوض غير معالج يوقف عملية HTTP.
- لا يوضع سر OAuth أو بيانات مستأجر في lease أو في سجل الخطأ.

## فحوص القبول ومنع الانحدار

1. `npm run check:session-resilience` يتحقق من وجود زوج الجلسة، تجديد
   single-flight وإعادة المحاولة الواحدة، ومنع المسح على `5xx`، وتفعيل
   العمال opt-in مع معالج خطأ وlease غير transaction-scoped.
2. `npm run build --workspace @baseer-erp/web` يثبت سلامة واجهة الجلسة.
3. `npm run build --workspace @baseer-erp/api` يثبت خدمات العامل والـlease.
4. قبل النشر: تطبق migration الخاص بـ`SystemSchedulerLease`، ثم يختبر تشغيل
   API أكثر من 10 ثوانٍ والعامل مفعّل في instance واحدة فقط، ويختبر سيناريو
   `401 → refresh → retry` وسيناريو رفض refresh.

لا يعتبر تغيير رسالة الواجهة وحده حلاً. يراجع هذا القرار عند إضافة cookie
آمن HttpOnly أو تطبيق متعدد tabs؛ عندها يحافظ على نفس خصائص الدوران وretry
والفصل بين خطأ المستخدم وخطأ الخدمة.
